# Конфігурація

Довідник по обох конфігураційних TOML-файлах `dnsqb-service`. Обидва — звичайний, редагований
вручну текст (SPEC.md §5), і обидва тепер мають другий, живий шлях запису через адмін-канал на
тому ж loopback `DoH`-порту: `resolver_config.toml` — `GET /admin/status`/`POST /admin/config`
(T-52), плюс `GET /admin/cache-config`/`POST /admin/cache-config/apply` (T-153) і
`GET /admin/geoip`/`POST /admin/geoip/add`/`remove` (T-77) для двох його вкладених таблиць;
`overrides.toml` — `GET /admin/overrides`/`POST /admin/overrides/add`/`remove` (T-47).
Ручна правка обох файлів лишається можливою; `POST /admin/reset` (T-149) перечитує обидва файли з
диска живцем, без перезапуску сервісу.

Обидва файли лежать в теці даних застосунку:

```
%LOCALAPPDATA%\dns-quorum-filter\resolver_config.toml
%LOCALAPPDATA%\dns-quorum-filter\overrides.toml
%LOCALAPPDATA%\dns-quorum-filter\geoip_maxmind.toml   (опційний, T-80 — див. нижче)
```

(`paths::app_data_dir` в коді — `crates/dnsqb-service/src/paths.rs`.)

> Формат — TOML, а не JSON (рішення T-145, `DECISIONS.md`) — саме заради підтримки коментарів і
> hand-editable стилю на кшталт `ssh_config`/`my.cnf`. Якщо в теці лежить старий
> `resolver_config.json`/`overrides.json` без відповідного `.toml`-сусіда, сервіс лише пише
> попередження в лог і ігнорує старий файл — автоматичної міграції немає.

* * *

## `resolver_config.toml`

Налаштування самого DoH-слухача. **Відсутній файл — це не помилка** (стартує з дефолтів нижче).
**Файл є, але зламаний (невалідний TOML, невідоме поле, `port = 0`, `timeout_ms = 0`,
`[cache].clamp_min_secs` більший за `clamp_max_secs` (T-153), `[geoip].blocked_countries` містить
код країни, що не є рівно двома ASCII-літерами (T-76), або файл більший за 64 КіБ) — це
фатальна помилка**: сервіс завершується з кодом 1, а не мовчки підставляє
дефолт (SPEC.md §1: жодного тихого fallback на інший порт). Ліміт розміру (T-58) — той самий захист
від необмеженої алокації, що вже застосований до DoH-повідомлень і адмін-запитів; 64 КіБ — з
великим запасом для чотирьох скалярних полів, навіть з великою кількістю коментарів.

| Поле | Тип | Дефолт | Опис |
|---|---|---|---|
| `port` | `u16` | `8443` | Порт локального DoH-слухача на `127.0.0.1`. `0` заборонено явно (`ConfigError::ZeroPort`) — динамічний порт означав би, що браузер, вручну наведений на конкретний порт, після рестарту мовчки перестає працювати. Привілейований порт (1-1023) не заборонений тут окремо — на Windows без підвищення прав бінд впаде голосно (`BindError::Other`), просто без спеціального пояснення "потрібні права адміністратора". |
| `timeout_mode` | `"fail_open"` \| `"fail_closed"` \| `"degraded"` | `"fail_open"` | Що вважати провайдера, який не відповів вчасно (SPEC.md §3.3). `fail_open` — не блокує (пріоритет доступності); `fail_closed` — блокує (пріоритет безпеки); `degraded` — вердикт як у `fail_open`, але неповнота позначається окремо в логах, і `stale-if-error` (T-28) до цього режиму не застосовується. |
| `timeout_ms` | `u32` | `2000` | Таймаут одного запиту до voter'а, у мілісекундах. `0` заборонено явно (`ConfigError::ZeroTimeout`) — інакше кожен запит миттєво отримує SERVFAIL, і фільтрація мовчки "ламається", виглядаючи як "інтернет лежить". |
| `[providers]` | вкладена таблиця | обидва `true` | Який саме quorum-провайдер опитується (T-148) — див. нижче. |
| `[cache]` | вкладена таблиця | див. нижче | TTL-межі та ємність кешу вердиктів (SPEC.md §4.1, T-153) — див. нижче. |
| `[geoip]` | вкладена таблиця | порожній список | Список заблокованих країн для GeoIP-фільтра (SPEC.md §3.5, T-76) — див. нижче. |

### `[providers]` — per-provider вмикання/вимикання (T-148)

```toml
[providers]
quad9 = true
adguard = true
```

| Поле | Тип | Дефолт | Опис |
|---|---|---|---|
| `quad9` | `bool` | `true` | Чи опитується Quad9 взагалі. |
| `adguard` | `bool` | `true` | Чи опитується AdGuard взагалі. |

Вимкнення **одного** провайдера не вимикає quorum — резолвер все одно опитує baseline і той
provider, що лишився увімкненим, і блокує за його сигналом (OR-логіка звужується до множини
активних voter'ів, не скасовується). Вимкнення **обох** — те саме, що старий `voters_enabled =
false`: явний pass-through через baseline-резолвер (SPEC.md §3/§8.1), не fail-closed і не тихий
no-op. Дозволи/блоклист (нижче) продовжують діяти незалежно від цього перемикача. Категорійне
вмикання поза межами цих двох Фаза-1-провайдерів (Ads/Adult тощо, `UI-SPEC.md` §3.4) — пізніша
фаза, не ця таблиця.

> **Міграція з попередньої версії**: до T-148 цей файл мав пласке поле `voters_enabled = true/false`
> замість таблиці `[providers]`. Це жорсткий перехід без сумісності: файл зі старим полем
> `voters_enabled` тепер провалює завантаження як невідомий ключ (`ConfigError::Toml`) — сервіс не
> стартує, поки поле не замінено на `[providers]` таблицю вище.

Приклад повного файлу:

```toml
port = 8443
timeout_mode = "fail_open"
timeout_ms = 2000

[providers]
quad9 = true
adguard = true
```

Файл можна лишити частковим — відсутнє поле (включно з окремим полем усередині `[providers]`)
бере дефолт з таблиці вище, а невідоме поле (одруківка на кшталт `potr` чи `adgaurd`) провалює
завантаження цілком, а не мовчки ігнорується — це стосується й полів усередині `[providers]`.

### `[cache]` — TTL-межі та ємність кешу вердиктів (SPEC.md §4.1, T-153)

```toml
[cache]
clamp_min_secs = 30
clamp_max_secs = 86400
block_verdict_ttl_secs = 86400
stale_grace_secs = 86400
max_capacity = 10000
```

| Поле | Тип | Дефолт | Опис |
|---|---|---|---|
| `clamp_min_secs` | `u64` | `30` | Нижня межа для TTL, отриманого від апстріму (`chain_cache_ttl`/`negative_cache_ttl`). |
| `clamp_max_secs` | `u64` | `86400` (24г) | Верхня межа для того самого. |
| `block_verdict_ttl_secs` | `u64` | `86400` (24г) | Час життя запису для BLOCK-вердикту — не походить від апстріму, окрема константа. |
| `stale_grace_secs` | `u64` | `86400` (24г) | RFC 8767 §5 stale-timer — вікно, протягом якого прострочений запис ще можна віддати при `stale-if-error` (T-28), поверх звичайного TTL. |
| `max_capacity` | `u64` | `10000` | Максимальна кількість записів у кеші (LRU-подібне витіснення понад це число). |

`clamp_min_secs` не може перевищувати `clamp_max_secs` — файл із таким поєднанням провалює
завантаження (`ConfigError::CacheClampMinExceedsMax`), а не мовчки застосовує якесь із двох значень:
`cache::clamp_ttl` сам собою залишається безпечним навіть проти інвертованої конфігурації (не панікує), але
"безпечний, попри неправильний ввід" — це не те саме, що "правильний ввід", тож помилковий файл
все одно відхиляється голосно на межі завантаження, той самий принцип, що й для `port = 0`/
`timeout_ms = 0` вище.

> **Зміна `[cache]` через адмін-канал скидає весь живий кеш вердиктів, не лише оновлює числа.**
> `max_capacity`/`stale_grace_secs` вшиті в саму структуру кешу (`moka::future::Cache`) при
> побудові — живого API змінити їх на існуючому екземплярі немає (перевірено читанням вихідного
> коду `moka` 0.12.16), тож будь-яка зміна `[cache]` будує новий, порожній кеш і підміняє ним
> старий. Наступний запит для кожного домену — це `cache miss`, навіть якщо змінилось лише
> `clamp_min_secs`.

### `[geoip]` — заблоковані країни для GeoIP-фільтра (SPEC.md §3.5, T-76)

```toml
[geoip]
blocked_countries = ["SE", "DE"]
```

| Поле | Тип | Дефолт | Опис |
|---|---|---|---|
| `blocked_countries` | `Vec<String>` (ISO 3166-1 alpha-2) | `[]` (порожній) | IP-адреса відповіді, що резолвиться в одну з цих країн, блокує всю відповідь (OR по кількох IP в одній відповіді). Кожен код — рівно дві ASCII-літери, нормалізується у верхній регістр при завантаженні; будь-що інше (`"RUS"`, одна літера, цифри) — фатальна помилка завантаження (`ConfigError::InvalidCountryCode`), не мовчазне ігнорування. |

**Порожній список за замовчуванням — свідоме opt-in рішення користувача, не політика застосунку
"з коробки"** (на відміну від Security-presets, SPEC.md §3.4, увімкнених за замовчуванням).
Причина — великі CDN (Cloudflare, Google, Amazon) роздають anycast-адреси, чия географія
змінюється між запитами й точками присутності: блокування країни ризикує заблокувати легітимні
сайти, які просто фізично проходять через дата-центр у цій країні, а не мають стосунку до її
юрисдикції. Це очікуваний, типовий ризик over-blocking для будь-якого сайту за CDN, не гіпотетичний
рідкісний випадок — тому веб-UI (нижче) показує явне попередження при кожному додаванні країни.

`GeoIP`-вердикт **ніколи не кешується разом із quorum-вердиктом** — застосовується живцем на
кожному читанні (і на кеш-хіт, і на свіжу quorum-відповідь), саме тому зміна цього списку діє
одразу на наступному запиті, без жодної логіки інвалідації кешу (SPEC.md §3.5). Сама база
(`.mmdb`-файл, DB-IP Lite за замовчуванням) — окремий механізм: фонова задача оновлення описана в
SERVICES.md, не в цьому файлі.

### Адмін-канал — живий запис `providers`/`timeout_mode` (T-52)

На тому самому loopback-слухачі, що й `/dns-query` (той самий TLS-сертифікат, той самий порт),
`dnsqb-service` віддає `GET /admin/status` (поточний живий стан + статистика з логу, включно з
`in_flight` — кількістю запитів, що резолвляться просто зараз, T-149) і приймає
`POST /admin/config` (JSON `{ providers, timeout_mode }`) — призначено для локального UI, не для
ручного виклику. З T-149 конфігурація подається браузером із самого `dnsqb-service`'s веб-UI
(`GET /admin/ui`, нижче), а не окремим Tauri-застосунком. Зміна застосовується **миттєво в
пам'яті** (наступний же запит бачить нове значення) і водночас пишеться назад у цей файл, якщо той
успішно завантажився з відомого шляху при старті.

> **Запис через адмін-канал перезаписує весь файл цілком, а не лише змінені поля** — будь-які
> ручні коментарі чи форматування, які ви додали в `resolver_config.toml`, буде втрачено після
> першої ж зміни через UI. Якщо файл важливо тримати людино-редагованим і прокоментованим — не
> користуйтесь UI-тумблерами для цього файлу, редагуйте його вручну (і перезапускайте сервіс).
> Це стосується й **ще не застосованої** ручної правки: якщо ви вручну змінили `port` чи
> `timeout_ms` у файлі, але ще не перезапустили сервіс, наступний же клік по тумблеру в UI
> перезапише файл значеннями з пам'яті працюючого процесу (тобто старим `port`) — ваша правка
> мовчки зникне, і браузер, наведений на новий порт, продовжить не працювати без видимої причини.

`port`/`timeout_ms` цим каналом не змінюються цього зрізу (лише `providers`/`timeout_mode`) —
зміна порту потребує перебіндингу слухача, поза межами живого застосування.

### Адмін-канал — живий запис `[cache]` (T-153)

`GET /admin/cache-config` (поточні живі значення) / `POST /admin/cache-config/apply` (JSON з тими
самими п'ятьма полями, що й таблиця `[cache]` вище, мінус `persisted`) — окремий маршрут від
`/admin/config` навмисно: якби поля кешу були частиною `AdminConfigUpdate`, кожен звичайний клік
по тумблеру провайдера мусив би теж пересилати поточний кеш-конфіг і тим самим **непомітно
скидав би весь кеш вердиктів** як побічний ефект незв'язаної дії. `Content-Type: application/json`
обов'язковий (той самий CSRF-гейт, `415` інакше); `clamp_min_secs > clamp_max_secs` у тілі
запиту — `400`, той самий валідатор (`CacheConfig::from_secs`), що й на завантаженні файлу.
Обидва маршрути (`/admin/config` і `/admin/cache-config/apply`) пишуть в один і той самий фізичний
файл через один і той самий внутрішній лок — конкурентні запити на різні секції файлу ніколи не
губ­лять одна одну.

### Адмін-канал — живий запис `[geoip]` (T-77)

`GET /admin/geoip` (поточний живий список) / `POST /admin/geoip/add` / `POST /admin/geoip/remove`
(обидва — JSON `{ "country": "SE" }`) — окремі маршрути від `/admin/config`/`/admin/cache-config/apply`
з тієї самої причини, що й `[cache]` вище: невʼязана зміна тумблера провайдера не повинна нести й
не повинна вимагати поточний список країн. Код валідується/нормалізується (верхній регістр)
однаково на обох маршрутах — і `add`, і `remove` — тим самим `validate_country_code`, що й
завантаження файлу; невалідний код на будь-якому з двох маршрутів — `400`, ніколи мовчазний
no-op. Додавання вже наявного коду — ідемпотентне, не дублікат. Усі три маршрути (`/admin/config`,
`/admin/cache-config/apply`, `/admin/geoip/add`/`remove`) пишуть в той самий фізичний файл через
той самий внутрішній лок, що й вище — жодна зміна не витирає сусідню секцію.

**На відміну від `[cache]`, зміна `[geoip]` нічого не скидає й не інвалідує** — GeoIP-вердикт
ніколи не кешується (див. вище), тож нова країна діє на найближчому наступному запиті без
жодного побічного ефекту на вже наповнений кеш.

### `POST /admin/reset` — м'який reset (T-149)

Той самий loopback-слухач, той самий CSRF-гейт (`Content-Type: application/json` обов'язковий,
інакше `415`). Перечитує **обидва** `resolver_config.toml`/`overrides.toml` з диска (той самий
шлях, з якого вони завантажились при старті) й атомарно підміняє живий стан — застосовується,
лише якщо **обидва** файли успішно завантажились; зламаний файл на диску повертає `500` і не
чіпає живий стан. Заразом очищує кеш і лог запитів. **Не є рестартом OS-процесу** — сам
`dnsqb-service` продовжує працювати; повний перезапуск процесу лишається за `dnsqb-watcher`
(SPEC.md §7, Фаза 3). Немає значення тіла запиту — POST з порожнім JSON-об'єктом (`{}`) достатній.

### `POST /admin/shutdown` — graceful завершення процесу (T-149)

Той самий loopback-слухач, той самий CSRF-гейт. **Найвищий blast radius на цьому каналі** —
шле сигнал (`tokio::sync::watch`) і одразу повертає `200`; сам процес `dnsqb-service`
завершується асинхронно (`hyper_util::server::graceful::GracefulShutdown`: нові з'єднання
більше не приймаються, активні дренуються з 5с таймаутом, ніколи `std::process::exit`, щоб не
вбити власну 200-відповідь цього ж запиту на півдорозі). DNS-резолюція для всієї машини після
цього мовчки йде через системний DNS, доки хтось вручну не перезапустить `dnsqb-service` —
`dnsqb-watcher` (Фаза 3) — єдине, що колись автоматично відновило б це, і його ще не існує.
Єдиний споживач — `dnsqb-tray`'s пункт меню "Зупинити фільтрацію" (SERVICES.md), захищений
нативним confirm-діалогом, що явно називає цей наслідок перед відправкою запиту.

### `GET /admin/ui` — вбудований веб-UI (T-149)

`dnsqb-service` сам роздає сторінку налаштувань на тому самому порту — `https://127.0.0.1:<port>/admin/ui`
(плюс `/admin/ui/main.js`, `/admin/ui/style.css`). Ті самі тумблери провайдерів/режиму таймауту,
що були в колишньому `dnsqb-ui` (Tauri-вікно, T-52 — видалено T-149, див. DECISIONS.md/
SERVICES.md), тепер у звичайному браузері: сторінка ходить у `/admin/status`/`/admin/config`/
`/admin/overrides` (T-47)/`/admin/cache-config` (T-153)/`/admin/geoip` (T-77) через `fetch()`
того самого походження (same-origin, CORS не потрібен). Сувора CSP
(`default-src 'self'; frame-ancestors 'none'`, без `unsafe-inline`) — жодного інлайн-скрипта/
стилю. **До кліку "Встановити сертифікат" у `dnsqb-tray` (T-49, автоматизовано, але не автоматично при
старті — SERVICES.md)** браузер покаже попередження про недовірений сертифікат перед самою
сторінкою — очікувано, не баг.

## `geoip_maxmind.toml` — опційний advanced-режим MaxMind GeoLite2 (SPEC.md §3.5, T-80/T-162)

За замовчуванням GeoIP-база — DB-IP Lite Country (без реєстрації, щомісячне оновлення,
`geoip_updater.rs`). Хто має власний **MaxMind**-акаунт і хоче частіші оновлення (GeoLite2 —
двічі на тиждень), задає креденшели в `/admin/ui` (картка «Джерело GeoIP: MaxMind GeoLite2» —
`POST /admin/geoip/maxmind`; кнопка «Очистити» = `POST /admin/geoip/maxmind/clear`, T-162) або,
як і раніше, редагує цей файл вручну:

```
%LOCALAPPDATA%\dns-quorum-filter\geoip_maxmind.toml
```

```toml
account_id  = "123456"
license_key = "ВАШ_MAXMIND_LICENSE_KEY"
```

| Поле | Тип | Обовʼязкове | Опис |
|---|---|---|---|
| `account_id` | рядок | так | MaxMind Account ID (той самий, що в `GeoIP.conf` `geoipupdate`; HTTP Basic-username при завантаженні). |
| `license_key` | рядок | так | MaxMind License Key (HTTP Basic-password). |

- **Файл відсутній** → DB-IP Lite (дефолт, незмінна поведінка).
- **Файл є, обидва поля непорожні** → MaxMind GeoLite2-Country: одне завантаження модерного
  permalink `https://download.maxmind.com/geoip/databases/GeoLite2-Country/download?suffix=tar.gz`
  з `Authorization: Basic` (ключ ніколи не в URL), опортуністична перевірка `.tar.gz.sha256`-
  сайдкара, розпаковка `.mmdb`-члена з `.tar.gz` (обмежена за розміром), та сама атомарна
  підміна файлу `geoip.mmdb`, що й для DB-IP.
- **Файл є, але зламаний / завеликий (>8 KiB) / порожнє поле** → у лог пишеться (без ключа!)
  попередження, і сервіс **відкочується на DB-IP Lite**, а не відмовляється стартувати.

> **Ключ зберігається у відкритому вигляді** — свідомий MVP-компроміс, той самий, що й для
> приватного ключа TLS-сертифіката (`key.pem`, SECURITY.md). T-162 обмежує ACL файлу поточним
> користувачем (той самий `icacls`-примітив, що й для `key.pem`) як interim-мітигацію; platform
> secure storage (DPAPI) — відкладено на **T-163**. `POST /admin/geoip/maxmind` після запису
> робить одну автентифіковану пробу проти MaxMind і повертає `check`
> (`VERIFIED`/`REJECTED`/`UNVERIFIED`) — оператор одразу бачить, чи прийнято ключ.
> Це окремий файл, а не таблиця в `resolver_config.toml` — інакше невʼязаний `POST /admin/config`
> міг би його мовчки перезаписати, повторюючи відомий клас багів проєкту; тому й лише один
> маршрут-писар, без спільного `persist_lock`.

> Зміна цього файлу (як через маршрут, так і вручну) набирає чинності лише при **перезапуску
> процесу** — на відміну від `resolver_config.toml`/`overrides.toml`, `POST /admin/reset` його не
> перечитує, і фоновий апдейтер тримає те джерело, з яким його заспавнили. Runtime-підхоплення —
> **T-163**.

## `overrides.toml`

Списки дозволів/блоків, які завжди перебивають quorum-вердикт (SPEC.md §5). При конфлікті
(один і той самий домен одночасно в обох списках) **завжди перемагає allowlist**.

```toml
allowlist = ["example.com", "*.trusted-cdn.example"]
blocklist = ["malware-example.test", "*.ads.example"]
```

| Поле | Тип | Опис |
|---|---|---|
| `allowlist` | `string[]` | Домени, які завжди резолвляться, минаючи quorum. |
| `blocklist` | `string[]` | Домени, які завжди блокуються (NULL-відповідь `0.0.0.0`/`::`), навіть якщо жоден upstream-провайдер їх не блокує. |

Синтаксис одного рядка:
- `example.com` — точний матч цього домену.
- `*.example.com` — суфіксний wildcard-матч (сам домен + всі піддомени). Це не regex і не
  substring-матч — зірка допустима лише як єдиний ведучий сегмент `*.`.

**Завантаження стійке до одного зламаного рядка**, але не до зламаного файлу цілком:
- Один рядок, що не парситься як валідний домен-патерн (порожній домен, `*` не на своєму місці,
  синтаксично невалідний домен) — пропускається, решта списку завантажується нормально.
  Причина повертається окремо, як `InvalidReason` (`UnexpectedWildcard` / `EmptyDomain` /
  `InvalidDomain`) — навмисно без самого тексту рядка, щоб домен ніколи не потрапив у
  diagnostic-лог (наскрізна вимога SPEC.md: жодних доменних імен у службових логах).
- Файл, який взагалі не є валідним TOML, або має невідоме поле (`blockList` замість
  `blocklist` тощо) — провалюється весь `OverrideLists::load` цілком (`OverrideError::Parse`,
  теж без тексту домену в повідомленні).
- Файл більший за 10 МіБ — провалюється весь `OverrideLists::load` цілком (`OverrideError::
  TooLarge`, T-58) без жодного читання вмісту в пам'ять. 10 МіБ — з великим запасом навіть для
  списку з десятками тисяч доменів; ліміт існує проти необмеженої алокації через адмін-канал
  (`POST /admin/reset` перечитує цей файл живцем, не лише при старті сервісу).
- Відсутній файл — це не помилка, стартує з порожніх списків.

> **На відміну від `resolver_config.toml`, зламаний або завеликий `overrides.toml` — не фатальна
> помилка.** `main.rs` ловить `Err` від `OverrideLists::load` (невалідний TOML, невідоме поле,
> **або перевищення 10-МіБ ліміту**) і стартує з **порожніми списками**, лише пишучи попередження
> в лог — сервіс продовжує працювати. Практично це означає: одруківка в назві поля, побитий TOML,
> чи випадково роздутий blocklist-файл — і сервіс мовчки (крім одного рядка в логах) резолвить усе
> без жодної фільтрації override-списками. Це свідомий вибір (SPEC.md: краще нефільтрований
> інтернет, ніж відмова стартувати взагалі), але саме тому це найважливіший факт цього розділу —
> не пропустіть попередження в логах після редагування файлу.

> **Той самий компроміс, що вже названий вище для `resolver_config.toml`, тепер стосується й
> цього файлу (T-47)**: `POST /admin/overrides/add`/`remove` перезаписує весь файл із живого
> стану при кожній зміні — незбережена ручна правка, зроблена між одним адмін-кліком і наступним,
> тихо перезаписується. Рядки, які на момент останнього завантаження (старт сервісу або
> `/admin/reset`) не розпарсились як валідний домен, **не втрачаються** — вони зберігаються в
> пам'яті окремо (`dispatch::OverridesState.invalid`) і дописуються назад дослівно при кожному
> `save()`, тож одна typo'вана правка вручну переживає наступний клік в UI, навіть якщо сама UI її
> не показує (список у `/admin/overrides` показує лише успішно розпарсені записи).

### `GET /admin/overrides` / `POST /admin/overrides/add` / `POST /admin/overrides/remove` (T-47)

Той самий loopback TLS-порт, той самий `Content-Type: application/json`-гейт на обох `POST`-
маршрутах, що й `/admin/config`/`/admin/reset` (CSRF-захист: не CORS-simple тип, тож
cross-origin `fetch()` без явного preflight ніколи не досягає реального запиту).

- `GET /admin/overrides` — повертає `{ allowlist: [{domain, is_wildcard}], blocklist: [...],
  conflicts: [domain, ...] }`. `conflicts` — домени, присутні як буквальний запис в обох списках
  одночасно (SPEC.md §5) — рахується сервером, не клієнтом.
- `POST /admin/overrides/add` — тіло `{ pattern, list }` (`list` — `"allowlist"`/`"blocklist"`).
  `pattern` — той самий формат, що й рядок файлу (`example.com` або `*.example.com`), парситься й
  нормалізується на сервері. Невалідний `pattern` — `400`. Додавання вже наявного запису —
  ідемпотентне, не помилка.
- `POST /admin/overrides/remove` — тіло `{ domain, is_wildcard, list }` (повна трійка, не лише
  `domain` — той самий домен може мати одночасно і точний, і wildcard-запис в одному списку).
  Видалення відсутнього запису — ідемпотентне, не помилка.

Обидва мутуючі маршрути одразу інвалідують відповідні записи кешу (`pipeline::invalidate_changed`,
T-40) — та сама вимога, що SPEC.md §5 явно називає ("при зміні списків — інвалідація відповідних
записів кешу"), і той самий механізм, яким уже користується `/admin/reset`.

## Що ще не реалізовано

- **Дія в один клік "додати в список з рядка логу" (T-46) ще не реалізована** — редактор
  override-списків сам по собі готовий (T-47, вище), але лог-екран/маршрут, з рядка якого мав би
  викликатись цей же `POST /admin/overrides/add`, ще не існує (T-54).
- **Нема category toggle** — `[providers]` перемикає лише два конкретні Фаза-1-провайдери
  (Quad9/AdGuard), не категорії (Ads/Adult тощо, `UI-SPEC.md` §3.4) — та вимагає нових upstream-
  presets, яких Фаза 1 не має.
- **Нема persisted query log config** — розмір/термін зберігання логу (SPEC.md §6: 1000 записів
  або 24 години) поки хардкоджені дефолти в `main.rs`, не в жодному з цих файлів (T-146,
  заблокований на T-96, шифроване сховище).
