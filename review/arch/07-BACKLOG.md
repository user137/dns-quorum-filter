## 1. Головний висновок

Blocker — жодного. Ядро (кворум, кеш, wire, сертифікат-лист, CSRF-гейт, ланцюг постачання,
відтворювана збірка) здорове: кешована відповідь — субмілісекундна, сертифікат — `CA:FALSE` зі
SAN лише для loopback, домени не потрапляють у сервісні логи, вбудовані дані не дублюються між
бінарями.

Що ламає місію, — не нестача фіч, а **три класи тиші**:
1. **Служба не стартує, і ніхто не каже чому** (ARCH-01, ARCH-03): зайнятий порт, битий конфіг,
   відкат версії → `exit(1)` → `GaveUp`; причина лише в прихованому лозі. Заплановане виправлення
   T-266 (хвиля 13) у цьому класі не допоможе: перезапуск дасть той самий збій.
2. **«Захищено» без знання, чи браузер узагалі ходить через службу** (ARCH-04): після першого
   налаштування жодного сигналу, якщо браузер з'їхав з DoH.
3. **Обіцянки приватності/економності, які код не виконує** (ARCH-20 — маркери без ротації,
   ARCH-14 — кеш читається таймінгом з чужих сторінок, ARCH-10 — повторні завантаження фідів).

Плюс одна економна аномалія, що зачіпає кожного: трей у простої їсть ≈2 % ядра (ARCH-19).

Опційні фічі поза кворумом за обсягом коду вже більші за саме ядро (≈4 540 проти 4 108 рядків).
Видаляти нічого не пропоную. Пропоную **не додавати нових фіч, доки не закриті класи 1–2**.

## 4. Топ-5 дій з найбільшим важелем для місії

1. **ARCH-03 + ARCH-01 до хвилі 13.** Єдиний шлях, де людина лишається без фільтра назавжди й не
   має жодної дії. Хвиля 13 без цього закриє лише половину класу `GaveUp`.
2. **ARCH-04 (а) у хвилю 3.** Одне поле DTO в уже запланованому бампі перетворює твердження
   «захищено» на чесне «я бачу запити браузера N хв тому» — найдешевший захист від найгіршого
   класу (тихий обхід: T-257, T-261, зміна браузера).
3. **ARCH-20.** Код суперечить письмовій гарантії приватності; виправлення — одна чиста функція
   й тест, а фонових запитів до трьох корпорацій стає втричі менше.
4. **ARCH-19 (а).** Кілька рядків у треї, ≈2 % ядра на кожному ноутбуці — найдешевший виграш для
   всіх користувачів одразу.
5. **ARCH-09.** Структурно закриває найчастіший баг-клас проєкту до того, як наступне поле конфігу
   відтворить його вчетверте.

## 5. Чого НЕ робити

- **Не додавати нових фіч** (нові джерела зон, нові бандли, нові картки), доки класи 1–2 з §1 не
  закриті: аудиторії бракує не функцій, а чесних сигналів.
- **Не видаляти опційні фічі** (бульбашка, персональна зона, GeoIP, бандли, ccTLD) — вони ізольовані,
  вимкнені за замовчуванням і не шкодять; ціна — лише підтримка (адресується ARCH-09).
- **Не автоповторювати старт після `GaveUp`** — SPEC §7 і рішення 2026-10-04; ARCH-03 саме про те,
  щоб *не* палити бюджет на детермінованих збоях.
- **Не міняти колір hero/значка за «давно не було запитів»** — браузер може бути просто закритий;
  це було б «завжди-увімкнене попередження» (SPEC §8.1). Лише текст.
- **Не вмикати перевірку `Sec-Fetch-Site` на `/dns-query` без експерименту** — якщо внутрішній DoH
  якогось браузера несе цей заголовок, фільтр перестане працювати для нього взагалі.
- **Не тягнути jsdom/Playwright** для UI-тестів, поки Proxy-DOM у `smoke.js` справляється (ланцюг
  постачання).
- **Не змінювати семантику персональної зони на реєстровані домени** без рішення в SPEC §5.1.1.

## 7. Знахідки, що не пережили огляд / уточнені

- **«GeoIP 7.7 МБ на кожен старт» як вимір** — лог встановленого застосунку містить лише перший
  старт після свіжої інсталяції, тож цього не доводить. Знахідка ARCH-10 тримається на **коді**
  (тіло качається до перевірки сайдкара), джерело переписано.
- **616 `CertificateUnknown` у лозі** — не новий баг: перші 20 хв після встановлення, до довіри
  сертифіката (зникли о 08:00 UTC). Лишилось лише як вимір для ARCH-21.
- **Подвоєння словників у бінарях** — не підтвердилось: лінкер відкидає невикористані дані
  (`grep -c -a` по релізних `.exe`).
- **Ризик сертифіката як CA** — не підтвердився: `CA:FALSE`, critical.
- **ARCH-19, «30 файлових операцій/с»** — для виміряного процесу ≈20 на тік-цикл (латч онбордингу
  вже закритий майстром); 30 — для наступних запусків.
