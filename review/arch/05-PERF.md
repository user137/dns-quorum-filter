## 1. Латентність для людини

`ВИМІРЯНО (MSIX-installed, curl 8.x без HTTP/2, HTTP/1.1 keep-alive)`:

| Шлях | Час | Що міряє |
|---|---|---|
| холодний запит (промах кешу), нове з'єднання | 0.155 с | TLS ≈0.031 с + fan-out до 3 провайдерів ≈0.12 с |
| кешований, нове з'єднання | 0.032 / 0.033 с | майже вся — TLS-рукостискання |
| **кешований, повторно використане з'єднання** | **0.16–0.34 мс** (4 запити) | реальний досвід браузера з keep-alive |

Холодний запит обмежений найповільнішим потрібним провайдером (OR-кворум з раннім виходом на «блок»,
`connect_timeout` 500 мс на апстрім — T-154(a)). Кешований — субмілісекундний. Для людини служба
непомітна; помітним буде лише перше відкриття нового сайту (~0.1 с додатково до звичайного DNS).

### Старт

`ВИМІРЯНО (MSIX-installed)`, логи першого запуску після свіжого встановлення:

| Подія | Час (UTC) | Δ |
|---|---|---|
| watcher: `started tray` | 07:40:03.130 | 0 |
| tray: `watcher is already running` (safety net) | 07:40:03.162 | +0.03 с |
| watcher: `started service` | 07:40:04.099 | +0.97 с |
| service: генерація сертифіката (перший запуск) | 07:40:04.120 | +0.99 с |
| service: `listening on https://127.0.0.1:8443` | 07:40:04.182 | **+1.05 с** |
| service: `GeoIP database refreshed` (7.7 МБ) | 07:40:05.268 | +2.14 с |

Від кліку на плитку до першої DNS-відповіді — близько 1 с; іконка трею — одразу (T-187, «трей
першим»). ≈0.97 с між спавном трею і спавном служби — послідовні `ensure_sibling_running`
(перевірка pid + спавн). **Не проблема.**

Після кожного рестарту кеш порожній (`persist_cache=false` за замовчуванням — свідомо, приватність),
тож перші хвилини всі запити холодні. Задокументований компроміс. Вікно без бандлів після рестарту —
ARCH-10 (Фаза 2).

## 2. Гарячий шлях

| Крок | Вартість | Оцінка |
|---|---|---|
| 1–2 overrides | O(n) лінійний прохід, двічі | виміряно в PERFORMANCE.md: ~10 000 записів ≈×4 p50 на дешевому шляху, суб-секунда; **не проблема** для реальних списків |
| 2b бандл (опційно) | до L хешувань `RandomState::hash_one` + `binary_search` у `Vec<u64>` (~5.5M → ≈23 порівняння на мітку) | ≈десятки випадкових доступів до ~44 МБ масиву на запит — мікросекунди; **не міряно**, але на порядки менше за fan-out |
| 3 ccTLD | `rsplit('.').next()` + порівняння з коротким списком | дрібниця |
| 4 кеш `moka` | O(1) | 0.16–0.34 мс разом із HTTP (виміряно вище) |
| 5 рейтинг-фільтр (опційно) | O(L) `HashSet` | дрібниця |
| **персональна зона (опційно)** | **`RwLock::write()` на кожен запит**; новий хост при 2000 записах → O(2000) прохід `min_by_key` під тим самим локом | ARCH-18 |
| 6 кворум | O(k) паралельно | мережа домінує |
| 7 GeoIP | mmap-пошук | дрібниця |

Конкурентність: `ConnectionGate` (семафор, без `Mutex`), ліміти рукостискання/простою (T-169).
Браузер тримає одне-два HTTP/2-з'єднання, тож сплеск при відкритті важкої сторінки — це потоки,
а не з'єднання. Живий навантажувальний тест не проводився (правило 9); попередні виміри
(3 000 одночасних TLS-рукостискань — 100 % успіху) у PERFORMANCE.md лишаються чинними для цього
шару.

```
[ARCH-18] severity: minor
Де: crates/dnsqb-service/src/personal_zone_stats.rs:247–285 (`record_visit`, `evict_oldest`);
  dispatch.rs:1384–1389
Категорія: продуктивність / місія (коректність опційної фічі)
Джерело: ПІДТВЕРДЖЕНО В КОДІ; частота досягнення ліміту — ГІПОТЕЗА
Три Б: user
Кому шкодить (аудиторія): лише тим, хто ввімкнув персональну зону (дефолт OFF). (1) Кожен
  DNS-запит бере ексклюзивний лок — під сплеском браузера запити серіалізуються на ньому
  (мікросекунди кожен, тож практично невідчутно). (2) Важливіше: `last_visited` має **денну**
  гранулярність, а записи — це **хости**, не реєстровані домени (без PSL). Коли за день набирається
  2000 унікальних хостів (CDN, трекери, піддомени), кожен новий хост витісняє **довільний** запис
  з найстаршим днем — а якщо всі записи сьогоднішні, то довільний сьогоднішній, включно з тим,
  який людина відкриває найчастіше. Навчена зона «мерехтить» — сайт то в бульбашці, то ні.
  Людина побачить лише, що улюблений сайт іноді блокується рейтинг-фільтром.
Що: витіснення за `min_by_key(last_visited)` по `HashMap` — при рівних ключах обирає перший у
  порядку ітерації, тобто випадковий.
Варіанти: (а) ключ витіснення `(last_visited, сума counts)` — спершу найрідше відвідувані з
  найстаршого дня; O(n) лишається, але n=2000 — дрібниця; (б) рахувати реєстровані домени через
  уже вбудований PSL (`public_suffix.rs`) замість хостів — менше записів, стабільніша зона, але
  змінює семантику (SPEC §5.1.1); (в) не чіпати.
Рекомендація: (а) — одна зміна ключа + тест «частий хост не витісняється потоком одноразових».
  (б) — розглянути, якщо фіча отримає реальних користувачів.
Тест / вимір: юніт: 2000 записів сьогоднішнього дня, один з них із counts=50, далі 100 нових
  хостів → частий запис живий. Скільки унікальних хостів на день у типового користувача —
  порахувати на `/admin/log` (лише кількість, без доменів) за день.
```

## 4. `already-filed` / свідомі компроміси

- Без single-flight: N однакових промахів → N fan-out — T-206 (характеризаційний тест),
  PERFORMANCE.md «No request coalescing (deliberate)».
- Порожній кеш після рестарту — наслідок `persist_cache=false` (приватність, задокументовано).
- Порожній бандл і повторне завантаження фідів після рестарту — ARCH-10.
- O(n) overrides — виміряно й прийнято в PERFORMANCE.md.
