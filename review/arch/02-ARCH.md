`ПІДТВЕРДЖЕНО В КОДІ` (`grep '^impl|^fn|^async fn' dispatch.rs`):

транзакції адмін-записів — ні. Ціна: **незручно** (2 570 рядків в одному файлі, 6 334 рядки тестів
поруч), не помилка сама по собі. Важливе — наслідок нижче (ARCH-09).

`orchestrate.rs` (1 012 рядків, 0 тестів) — те саме для старту; див. ARCH-03 (Фаза 1) і Фазу 3.

## 2. Стан і власники

### `persist_lock` і клас «застарілий знімок»

`ПІДТВЕРДЖЕНО В КОДІ`: у `dispatch.rs` **7 рукописних літералів `ResolverConfig { … }`** (рядки
1831, 2417, 2577, 2755, 2866, 2958, 3305), кожен на 14 полів; 7 викликів `config.save` під
`persist_lock` (10 захоплень разом із `overrides_persist_lock`). Кожен сайт вручну перелічує, яке
поле брати з живого `RwLock`, а яке — з будівельного `PersistTarget`.

```
[ARCH-09] severity: major
Де: crates/dnsqb-service/src/dispatch.rs:1831,2417,2577,2755,2866,2958,3305
Категорія: архітектура
Джерело: ПІДТВЕРДЖЕНО В КОДІ; історія класу — ВЖЕ ЗАФІКСОВАНО (DECISIONS.md, Батч 4.5 «(є)»;
  T-217; CLAUDE.md «single most recurring bug class»; Батч 7.3)
Три Б: user
Кому шкодить (аудиторія): людина змінює налаштування А на сторінці, потім Б — і після рестарту
  А «саме відкотилось». Не помітить, доки не перезавантажить комп'ютер; причину не знайде.
Що: клас багу виправлявся **поштучно** щонайменше тричі (T-57/T-139/…, T-217, Батч 7.3), але
  його структурна причина — N рукописних збірок повного конфігу — лишилась і росте: кожне нове
  поле (`cctld_block` у Фазі 5 — останнє) треба правильно дописати в 7 місць. Компілятор ловить
  лише *відсутнє* поле, а не *застаріле джерело* (`state.persist.x` vs `x_snapshot()`).
  Структурного рішення ніде не зафіксовано (grep TASKS/DECISIONS/review за builder/helper/«один
  конструктор» — порожньо).
Варіанти:
  (а) одна функція `AppState::live_resolver_config(&self) -> ResolverConfig` (усі поля з живих
      знімків; `port`/`limits`/`persist_*` — з `PersistTarget`, бо не мутуються в рантаймі) +
      `fn persist_config_with(&self, mutate: impl FnOnce(&mut ResolverConfig)) -> bool` під
      `persist_lock`. 7 літералів → 7 замикань по 1–3 рядки. **Дорого** лише за обсягом diff
      (~300 рядків), логіку не змінює. Новий тест «кожне поле, змінене маршрутом А, виживає
      запис маршрутом Б» — таблицею по всіх парах.
  (б) лише тест-матриця пар маршрутів (без рефакторингу) — ловить регресію, не прибирає
      причину.
  (в) не чіпати — покладатися на ревʼю.
Рекомендація: (а) — до наступного нового поля конфігу. Поєднати з виносом `AppState` і `apply_*`
  з `dispatch.rs` в окремі модулі (стан / адмін-транзакції), щоб `dispatch` став таблицею
  маршрутів.
Тест / вимір: property/таблиця: для кожного маршруту-писача M1 і кожного іншого M2 — змінити
  поле через M1, викликати M2, перечитати `resolver_config.toml` → поле M1 збережене.
```

### Durable vs in-memory після рестарту

```
[ARCH-10] severity: major
Де: crates/dnsqb-service/src/blocklist_updater.rs:16–20, 552–562, 585–670;
  geoip_updater.rs:285–320; topn_updater.rs:99–108
Категорія: архітектура
Джерело: ПІДТВЕРДЖЕНО В КОДІ — `try_user_country_release` (`geoip_updater.rs`) спершу
  безумовно качає тіло (`fetch_bounded(USER_COUNTRY_URL)`), і лише потім `.sha256`-сайдкар для
  перевірки; `topn_updater::refresh_one_list` (`:175–179`) — той самий порядок; у бандлів сайдкара
  немає взагалі. Умовного запиту (ETag / If-Modified-Since / «сайдкар збігся — тіло не качати»)
  немає ніде. Розмір `geoip.mmdb` — 7 717 259 байт (`ls`, MSIX-installed). Лог встановленого
  застосунку цього **не доводить** (там лише перший старт після свіжої інсталяції, де завантаження
  очікуване за будь-якого дизайну).
Три Б: user | lower-layer
Кому шкодить (аудиторія):
  1) хто ввімкнув публічні блок-списки: **після кожного рестарту служби** (перезавантаження,
     рестарт від watchdog, оновлення) бандл у памʼяті порожній, доки всі обрані джерела не
     завантажаться **послідовно** (цикл `for source in …`, таймаут на джерело — 600 с), і всі
     вони (≈111 МБ) качаються наново. Картка бандлів показує по джерелах «завантажується…»
     (`uk.json` `blocklist.status.loading`), але hero і значок — «захищено»/зелений, а
     `blocklist_bundles_is_active` дивиться лише на `enabled`. Хто не відкриває сторінку — не
     помітить.
  2) усі: GeoIP-база (7.7 МБ) завантажується наново на **кожному** старті служби, навіть
     коли список заблокованих країн порожній (дефолт; сама база потрібна й тоді — для країни в журналі, T-161, але не щостарту). Задумано раз на 24 год.
Що: усі три оновлювачі — `loop { refresh; park(24h) }` без перевірки віку файлу на диску.
  Коментар `geoip_updater.rs:285` пояснює негайний перший цикл потребою свіжої інсталяції
  («fresh install gets a database right away»), але той самий шлях спрацьовує і на кожному
  звичайному рестарті. Для бандлів warm-load з диска (`load_blocklist_bundles_from_disk`)
  написаний, але свідомо не підключений (Батч 7.3, через ~111 МБ синхронного читання на старті).
Варіанти:
  (а) перший цикл кожного оновлювача: якщо файл на диску молодший за інтервал — не качати,
      а запаркуватись на залишок (mtime уже є «last success» за конвенцією модулів); для
      бандлів — warm-load з диска у `spawn_blocking` **після** того, як listener почав
      приймати (не блокує старт), потім звичайний цикл. Невеликий обсяг, патерн є.
  (б) ~~лише GeoIP: не качати, поки `blocked_countries` порожній~~ — **відкликано при ревізії
      хвиль:** база потрібна й за порожнього списку — `geoip::resolved_ip_country` анотує країною
      кожен рядок журналу (T-161, CLAUDE.md), тож (б) прибрав би фічу.
  (б′) GeoIP і top-N: спершу сайдкар `.sha256` (кілька байтів), і якщо він збігається з хешем
      файлу на диску — тіло не качати. Працює й на 24-год циклі, не лише на старті.
  (в) не чіпати.
Рекомендація: (а) для всіх трьох + (б′). Закриває і вікно без бандла, і мережеву ввічливість
  (повторне завантаження після кожного ребуту — поза поведінкою «раз на добу»).
Тест / вимір: юніт `first_cycle_delay(now, mtime, interval)` (чистий); наживо — два рестарти
  поспіль, у лозі один «refreshed», mtime `geoip.mmdb` не змінюється.
Перевірка «вже відомо»: KNOWN-LIMITATIONS.md має «stale non-empty set» (протилежний випадок) і
  integrity-обмеження; про повторне завантаження на старті й порожнє вікно — нічого.
```

### Інше про стан (без нових знахідок)

- §7.1 #7 single-writer для `watchdog-state.json` — тримається (`watcher` — єдиний писач;
  `stop.flag`/`quit.flag` — окремі файли). `ПІДТВЕРДЖЕНО` переліком у Фазі 0.

  персональної зони. Задокументовано (`log_persist`), прийнятно.

  один воркер на мілісекунди на одну адмін-дію. **Не проблема на цьому масштабі.**

`resolver_config.toml` без версії + `deny_unknown_fields` означає: **старіша збірка на новішому
конфігу** (відкат версії вручну) → `Err` → `exit(1)` → `GaveUp` (клас ARCH-03). MSIX за
замовчуванням не дає поставити старішу версію поверх новішої, тож ймовірність мала —
**не проблема на цьому масштабі**, але це ще один вхід у той самий клас «фатальний старт без
пояснення»; закривається тим самим рішенням ARCH-03 (а), окремої знахідки не заводжу.

Атомарність запису конфігів — ARCH-01 (Фаза 0).
