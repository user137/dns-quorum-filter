## Ground Truth Rule — читати перед малюванням чи оновленням будь-якої діаграми

**Діаграма має відтворювати те, що код (чи, до появи коду — SPEC.md) насправді
каже, перевірене читанням — ніколи те, що здається правдоподібним, симетричним
чи "ймовірно так це працює".** Конкретно:

- Кожна стрілка, гілка й підпис мають трасуватись до конкретного розділу
  SPEC.md (чи файла:рядка коду), який ти справді прочитав у поточній сесії.
  Не відкривав файл — не знаєш гілки, іди читай.
- Не згладжуй асиметричну чи "негарну" структуру в охайну діаграму. Якщо
  джерело описує дві незалежні умови без явного порядку між ними — малюй саме
  це, не три чисті паралельні гілки.
- Не виводь порядок виконання з того, що було б "природно" — перевіряй.
- Де джерело не називає щось, для чого діаграмі потрібен підпис (наприклад,
  групування кількох станів у одну мітку) — підпис має супроводжуватись
  буквальною умовою з джерела, яку він позначає. Ніколи не лишай вигаданий
  підпис так, ніби це реальний enum чи стан у коді/спеку.
- Якщо під час малювання діаграма не збігається з щойно прочитаним джерелом —
  це сигнал: або діаграма була неправильна, або в джерелі реальна прогалина.
  Звітувати про обидва варіанти, не мовчки обирати зручніший.
- При оновленні діаграми після зміни джерела — перевивести зачеплену частину
  з нового джерела, не редагувати стару діаграму за патерном її попередньої форми.

Порушення цього робить діаграму гіршою за її відсутність: неправильна
діаграма — це довірена документація, яка бреше.

## Синхронізація діаграм ↔ документів (обов'язковий ритуал)

Діаграми тут — виконуваний контракт логіки системи, не ілюстрації. Вони
мусять завжди відповідати SPEC.md (і, згодом, коду). Будь-яка зміна логіки
в SPEC.md/CLAUDE.md = обов'язковий прогін звірки діаграм, як інтеграційний
тест після зміни коду.

### Коли спрацьовує (тригери)

Перед завершенням БУДЬ-ЯКОЇ з дій:
- зміна конвеєру рішень, порядку кроків, станів у SPEC.md чи CLAUDE.md
- зміна DTO-полів, enum-значень, каналів UI↔backend
- зміна фазового плану (що в якій фазі)
- створення нового розділу SPEC.md, що описує логіку чи UI
- видалення/злиття секцій, що описують поведінку

Чисто текстові правки (формулювання, друкарські) тригер НЕ вмикають.

### Що зробити (механічний чеклист — звітувати по КОЖНОМУ пункту)

1. ВИЗНАЧ зачеплені діаграми: відкрий кожен файл у цій папці, перевір блок
   SOURCES угорі. Випиши, які діаграми посилаються на змінений розділ.
2. ПРОЙДИ кожну зачеплену діаграму проти оновленого тексту SPEC.md/CLAUDE.md:
   чи всі стани/переходи/поля ще існують? чи з'явились нові, яких нема в
   діаграмі? чи не зник елемент, який діаграма ще показує?
3. КЛАСИФІКУЙ кожну розбіжність: діаграма відстала → онови точково; діаграма
   права, джерело суперечливе → познач ⚠️ GAP і повідом користувача, не латай
   самовільно.
4. НОВА логіка без діаграми → створи нову (тип за змістом: stateDiagram для
   автомата, sequenceDiagram для взаємодії, flowchart для рішень/структури;
   не форсуй automaton там, де умови незалежні — див. приклад
   `ui-status-indicator.md`).
5. ОНОВИ блок SOURCES у кожній зміненій/новій діаграмі.
6. ОНОВИ цей індекс.

### Залізні правила

- Малюй/оновлюй РІВНО за джерелом. НЕ латай відсутні переходи "бо логічно" —
  познач ⚠️ GAP.
- Звірка — обов'язкова перед "готово", не опційна.
- У фінальному звіті будь-якої зміни SPEC.md/CLAUDE.md додавай рядок:
  "Звірка діаграм: [не потрібна / прогнано, зачеплено N діаграм, оновлено M,
  GAP: K]".
- Трасування (блок SOURCES) якорити на СТАБІЛЬНІ орієнтири — номери й назви
  розділів SPEC.md (§3.4, §8.1 тощо), не на номери рядків (ті зсуваються при
  будь-якій правці).
