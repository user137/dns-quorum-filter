# DNS Quorum Blocker — технічний спек проєкту

## Суть ідеї

Кросплатформний лайтвейт-застосунок, що піднімає локальний DNS-over-HTTPS (DoH) сервер
на `127.0.0.1`, до якого браузер (через вбудовану опцію "Custom DoH provider") відправляє
всі DNS-запити. Застосунок опитує паралельно кілька публічних фільтруючих DNS-провайдерів
(Quad9, AdGuard DNS та ін.) і приймає рішення про блокування домену за принципом **кворуму
(OR-логіка: блокувати, якщо хоч один провайдер каже "блок")**.

Це **не** конкурент uBlock Origin — це мережевий (DNS-level) фільтр, не заміна
element-picker / cosmetic filtering / URL-pattern blocking, які робить uBlock. Ціль:
покрити malware/phishing/adult/ads на рівні резолюції домену, використовуючи одразу
кілька незалежних джерел threat-intelligence замість одного провайдера.

## Чому саме такий дизайн (стисло, з обговорення)

- **Чому не browser extension з live-запитами:** Manifest V3 (`declarativeNetRequest`)
  не дозволяє синхронно блокувати конкретний HTTP-запит за результатом асинхронного
  DoH-лукапу в реальному часі — правила мають бути зареєстровані заздалегідь. Firefox
  ще підтримує blocking `webRequest`, Chrome — ні.
- **Чому не system-wide DNS override (`127.0.0.1:53` + системні DNS-налаштування):**
  немає надійного кросплатформного механізму гарантованого відкату при краху процесу.
  На Windows це задокументована, невирішена проблема навіть у зрілих продуктів
  (NextDNS Windows app "втрачає контроль" над DNS-налаштуваннями, користувачі
  обходять scheduled task'ом). macOS має правильний примітив (Network Extension
  framework з автоматичним відкатом ОС), Windows — ні. **Переоцінено 2026-08-29 (TASKS.md
  T-157, повний аналіз там)**: цей пункт передбачав лише один системний варіант (plain DNS на
  порту 53). З'явився й другий, раніше не розглянутий — Windows-native DoH-клієнт
  (`Add-DnsClientDohServerAddress`, підтверджено для Windows Server 2022 напряму з Microsoft Learn;
  для Windows 10/11 client — Ф1-ціль проєкту — лише за вторинними джерелами, не перевірено прямо),
  який *якщо* приймає loopback-шаблон, переюзовував би вже наявний DoH-сервер і вже підтверджений
  cert-trust механізм (§2) замість
  нового raw-DNS-прото-хендлера. Це не змінює висновок цього пункту — crash-recovery ризик
  однаковий для plain-DNS і DoH-варіантів системного заміщення, бо стосується самого факту "один
  системний резолвер замінює всі інші", не протоколу — і live-перевірка 2026-датованих NextDNS
  баг-репортів (T-157) підтвердила, що ця проблема й сьогодні не вирішена, не застаріла з моменту
  першого написання цього розділу. Названо як третій кандидат для майбутньої, явно опційної
  (не заміна цього дизайну) фічі, не як перегляд цього рішення.
- **Чому custom DoH provider в самому браузері:** знімає обидві проблеми вище. Якщо
  локальний DoH-сервер падає — ламається тільки DNS-резолюція в конкретному браузері
  (браузер сам має fallback-логіку), а не весь інтернет на машині. Не потребує
  постійних адмін-прав (тільки одноразово — для довіри локальному сертифікату).
- **Чому OR, а не merge локальних списків:** частина даних (malware/phishing-фіди
  типу Quad9) — пропрієтарна threat-intelligence, доступна тільки через live-запит,
  без публічного сирого списку для локального мержу. Для публічних списків
  (EasyList/AdGuard base) live-запит не має сенсу — там доцільніший локальний кеш,
  але для MVP не критично.

виявився окремим, не довготривалим процесом (SERVICES.md: "обидва [`dnsqb-service`/

відкритим цілком окреме питання: як Rust-ядро *того* процесу взагалі дізнається живий стан

що вже названо для майбутнього `/health`, ряд 3), а не відкривати новий мережевий слухач чи інший

**T-149 замінило єдиний "UI" на два окремих процеси, кожен зі своїм каналом до `dnsqb-service`**
(рядки 12a/12b вище) — `dnsqb-tray` (довготривалий фоновий трей, дії/статус) і звичайний браузер
(повне налаштування, `/admin/ui`). Рядок 4 (Tauri IPC) більше не існує — обидва нові учасники
спілкуються з `dnsqb-service` виключно через рядки 12a/12b, той самий HTTP-адмін-канал, ніякого
внутрішньопроцесного мосту немає взагалі, бо жоден із двох більше не той самий процес, що й
`dnsqb-service`.

### 1. Local DoH server

- Слухає **виключно** `127.0.0.1` (ніколи `0.0.0.0`) — прибирає клас атак ззовні
  мережі на рівні конфігурації, а не політики.
- Реалізує RFC 8484 (DoH: GET/POST, `application/dns-message`).
- Ендпоінт: `https://127.0.0.1:<port>/dns-query`.
- **Порт — фіксований за замовчуванням, конфігурований**. Динамічний порт ламає
  ручне налаштування в браузері (при кожному старті адреса змінюється). Якщо
  дефолтний порт зайнятий — не мовчазний fallback на інший, а явна помилка в UI
  з пропозицією змінити порт у налаштуваннях.

### 2. Сертифікат для локального DoH — **БЕЗ власного CA**

**Рішення: не генерувати локальний CA. Тільки один self-signed leaf-сертифікат
на `127.0.0.1`, доданий у trust store як довірений для цього конкретного хоста.**

Обґрунтування (це найбільша поверхня атаки в проєкті, більша за весь DNS-код):
довірений у системі CA, чий приватний ключ лежить на диску користувача, дозволяє
будь-кому, хто цей ключ дістане (malware, вкрадений бекап, синхронізація папки
в хмару), випустити валідний сертифікат на **будь-який домен** — банк, пошту,
будь-що — і браузер прийме його без попереджень. Це повний MITM усього HTTPS-трафіку.
Відома проблема класу mkcert (у них це прямо в README як попередження): для
локального dev-інструменту прийнятно, для масового продукту — ні.

З leaf-сертифікатом компрометація ключа дає атакувальнику максимум підміну
localhost, а не всього інтернету. Blast radius менший на порядки.

**Ця властивість емпірично підтверджена 2026-08-29, а не лише виведена з
теорії RFC 5280.** До цього моменту `IsCa::ExplicitNoCa` (`cert.rs`) і твердження
вище про "максимум підміна localhost" були пов'язані лише логічно (кодуємо
`cA=FALSE` → RFC 5280 каже, що конформний валідатор шляху не повинен приймати
такий сертифікат як емітент) — жоден живий тест не перевіряв, що саме Chrome's
верифікатор цю вимогу насправді виконує для сертифіката, довіреного через
`CurrentUser\Root`-override (а не через звичайний PKI-ланцюг). Мотивація перевірки:
занепокоєння користувача, що весь механізм "leaf напряму в Root" — нестабільний
хак; T-157 (аналіз системного DNS через `127.0.0.53`) виник частково з цього
занепокоєння. **Живий тест**: розширений probe (той самий сценарій, що й T-49/T-51,
`rcgen::Issuer::from_params` над параметрами довіреного leaf-сертифіката) видав
другий, "evil"-лист для `127.0.0.2` з новим ключем, але підписаний приватним
ключем **того самого** довіреного leaf-сертифіката (точна модель "атакувальник
украв приватний ключ і намагається випустити сертифікат на інший хост") — evil-лист
ніде в жоден trust store не додавався, лише довірений leaf. Результат: Chrome
відкрив `https://127.0.0.1:18443/` (довірений leaf) без жодних попереджень, і
одразу видав помилку сертифіката на `https://127.0.0.2:18444/` (evil-лист) —
підтверджує, що Chrome's верифікатор дійсно застосовує `basicConstraints`/`cA=FALSE`
при побудові шляху навіть через `CurrentUser\Root`-override, не лише для звичайних
публічно-довірених CA-ланцюгів. **Висновок для занепокоєння користувача**: сам
механізм довіри (Chrome's "local trust decisions", підтверджено офіційною
Chromium FAQ, live WebFetch 2026-08-29) — не недокументований хак, а свідома,
підтримувана Chrome-командою поведінка, якою користуються mkcert/Fiddler/корпоративні
MITM-проксі; і структурний захист від leaf-компрометації (`cA=FALSE`) реально
працює, не лише декларація в коментарі. Залишковий, не знятий цим тестом ризик —
операційний, не архітектурний: точна вимога "саме `Root`, не `TrustedPeople`"
ніде офіційно не задокументована (знайдено емпірично, T-49/T-51), і `Root`-стор —
підтверджено активна ціль сигнатурного сканування AV/EDR (травень 2026,
хибне спрацювання Microsoft Defender на легітимних DigiCert root-сертифікатах,
live WebSearch) — не доказ, що цей конкретний leaf колись поставить хибне
спрацювання, але підтверджує, що `Root`-стор — це місце, за яким реально стежать,
а не нейтральна територія.

Вимоги до реалізації:
- SAN обов'язково: `IP:127.0.0.1`, `IP:::1`, `DNS:localhost`.
- Приватний ключ — у платформному secure storage (Windows DPAPI / macOS Keychain /
  Linux Secret Service), **ніколи не plaintext-файлом поруч із конфігом**. Якщо
  на MVP-етапі це складно — файл із правами `600` у app data, але це технічний
  борг, зафіксований явно, а не дефолт назавжди.
  - **Реалізовано, T-67 (2026-08-31).** Ключ живе у Windows Credential Manager
    через крейт `keyring` (`key_store.rs`); на диску лишається тільки публічний
    `cert.pem`. Ім'я запису прив'язане до app-data-теки
    (`dns-quorum-filter` / `doh-tls-private-key:<sha1(теки)[..8]>`), тож
    ізольований scratch-екземпляр не конфліктує з реальним (шлях нормалізується
    перед хешуванням — lowercase + без кінцевих сепараторів — щоб `dnsqb-tray`,
    що виконує ротацію в окремому процесі, вивів те саме ім'я). Plaintext
    `key.pem` від pre-T-67-інсталяції одноразово копіюється у сховище
    (`cert::migrate_legacy_key_into_store`) і видаляється з зануленням
    (`discard_legacy_key_file`) **лише після** того, як `tls` підтвердив, що
    збережений ключ підходить до `cert.pem` — невідповідний plaintext-ключ
    ніколи не знищується першим; поточний довірений сертифікат зберігається.
    `unsafe` Win32-FFI лежить у
    `windows-native-keyring-store`, тож крейт-широкий `#![forbid(unsafe_code)]`
    `dnsqb-service` не порушено. Дворазова `icacls`-ACL-послідовність (T-50)
    прибрана в T-163 разом з останнім plaintext-секретом на диску — MaxMind-
    креденшели теж переїхали в secret store (`key_store::maxmind_credentials_entry`),
    тепер `dnsqb-service` не пише на диск жодного секрету. macOS Keychain / Linux
    Secret Service `keyring` абстрагує, але тут не перевірено (немає доступу до
    цих платформ) — **T-71**.
    Вибір `keyring` замість точкового `unsafe` DPAPI-виклику — рішення
    користувача (план T-67), саме заради збереження forbid-інваріанта й
    forward-fit під T-71.
- Ротація: сертифікат довгоживучий, але з механізмом перевипуску; при перевипуску
  старий видаляється з trust store, не накопичується.
  - **Реалізовано, T-69 (2026-08-30).** Дія трею "Перевипустити сертифікат" (за
    підтвердженням через нативний діалог, поруч зі "Встановити"/"Видалити") —
    `dnsqb_service::rotate_certificate` як упорядкована композиція наявних
    примітивів, без нового примітиву видалення: `generate_self_signed_cert` →
    `trust_store::uninstall` (CN-вичерпний, прибирає **всі** старі записи цього
    проєкту) → `write_cert_and_key_to_app_data` → `trust_store::ensure_installed`.
    Порядок "очистити перед записом" вимушений: новий сертифікат має той самий
    `CommonName`, тож `uninstall` після встановлення видалив би і його. Вікно
    валідності лишається фіксованим (2020–2120), не generation-relative —
    свідоме рішення, ротація його не потребує. Новий сертифікат починає діяти
    лише після ручного перезапуску `dnsqb-service` (процес тримає свій
    `rustls::ServerConfig` від старту; hot-reload TLS — поза межами задачі); до
    перезапуску сервіс віддає попередній сертифікат, якого вже нема в trust store,
    тож браузер показує попередження про недовірений сертифікат на `/admin/ui`.
    Повний запис — `TASKS-DONE.md`, T-69.
- Деінсталятор **зобов'язаний** видалити сертифікат із trust store. Залишений
  довірений сертифікат після видалення програми — окремий баг безпеки.

Встановлення в trust store (єдиний момент потреби підвищених прав — одноразово):
- **Windows — автоматизовано, T-49 (2026-08-29), не ручна інструкція.** `certutil -addstore -user
  Root` / `-delstore -user Root`, довіра Chrome/Edge (обидва читають системний store). Емпірично
  підтверджено 2026-08-29: самопідписаний leaf-сертифікат для Chrome треба саме в `Root` (Trusted
  Root Certification Authorities), не в `TrustedPeople` — останнє не спрацювало на живому тесті,
  хоча концептуально мало б підійти для довіри одному конкретному end-entity-сертифікату без
  CA-прав; `-user Root` не потребує адмін-прав. Дві симетричні дії в `dnsqb-tray` ("Встановити
  сертифікат"/"Видалити сертифікат"), кожна за підтвердженням через нативний діалог — свідомо не
  тихий автозапуск при старті `dnsqb-service`. **Підтверджено живим тестом користувача 2026-08-29**:
  `certutil -addstore -user Root` не тихий — Windows показує власний, окремий діалог "Попередження
  системи безпеки" поверх застосункового підтвердження (два послідовні діалоги на одну дію, не
  один) — UX-незручність цього дублювання зафіксована окремо, TASKS.md T-158. Повний раунд-тріп
  також підтверджено: після встановлення сайт довірений, після видалення попередження повертається.
  Ідентичність сертифіката для встановлення — SHA-1
  thumbprint поточного `cert.pem` (не CommonName, який лишається сталим і після перевипуску
  сертифіката); для видалення — навпаки, CommonName (щоб прибрати геть усі записи цього проєкту,
  включно зі "застарілими" після перевипуску, не лише той, що відповідає поточному файлу). Повний
  запис — `TASKS-DONE.md`, T-49.
- **macOS** — Keychain (`security add-trusted-cert`), довіра Safari/Chrome.
- **Firefox — окрема NSS-база на КОЖНІЙ платформі, не лише Linux.** Firefox ніколи не читає
  системний trust store (ні Windows Certificate Store, ні macOS Keychain) — власна NSS-база
  (`cert9.db`) у кожному профілі користувача, крос-платформно. Два механізми: (1) NSS-власний
  `certutil` (інший бінарник, ніж Windows' `certutil.exe`, з пакета NSS/`nss-tools`) напряму пише в
  профіль; (2) Mozilla Enterprise Policy — `policies.json` із ключем `Certificates.Install`,
  офіційно підтримуваний механізм, Firefox сам імпортує сертифікат при старті, не потребує NSS-
  бібліотеки в застосунку. Жоден з двох не автоматизований на Ф1 (нижче, T-132) — ручна інструкція.
- **Linux** — додатково до Firefox-розколу вище, Chrome/Chromium на Linux теж тримає окрему NSS DB
  (`~/.pki/nss/db`), не системний store. Нетривіально — окремий epic, див. "Поза межами MVP".

### 3. Quorum resolver

- Паралельні async-запити до N апстрім-DoH-провайдерів.
- Політика: **OR** (block, якщо хоч один провайдер блокує) — базова політика проєкту.
- Апстрім-з'єднання — тільки TLS зі **стандартною валідацією** сертифіката. Жодних
  bypass/self-signed тут; self-signed стосується виключно локального сертифіката
  для браузера.
- **Кворум застосовується тільки до A / AAAA.** Решта типів записів (MX, TXT, SRV
  і особливо **HTTPS/SVCB**) проксіюються до одного апстріму без кворум-логіки.
  Причина: Firefox використовує HTTPS RR для отримання ключів ECH (Encrypted
  Client Hello) — некоректна обробка цього типу тихо вимикає ECH у користувача.
- **TTL при розбіжності між провайдерами — брати мінімальний** (консервативно).
- **Порожній набір voters (усі провайдери вимкнені користувачем) — явний
  pass-through, не `fail-closed` і не мовчазна поведінка "як є".** OR-логіка
  над порожньою множиною семантично некоректна — трактувати як свідоме
  рішення користувача вимкнути фільтрацію повністю: резолюція йде через
  baseline-резолвер (3.4) без фільтрації. UI зобов'язаний показати це окремим,
  явним станом індикатора (8), відмінним від "деградований апстрім" — не збій,
  а явний вибір, про який користувач має точно знати. Знайдено через
  misuse-тестування каналу UI↔бекенд (8.1) — раніше в спеку цей стан не був
  визначений явно.

#### 3.1. Розпізнавання блоку — `is_blocked(response)`

Провайдери сигналізують блок по-різному; предикат провайдер-специфічний і має бути
явною таблицею в конфігу, а не вгаданою евристикою:

| Провайдер     | Типова сигнатура блоку |
|---------------|------------------------|
| Quad9         | NXDOMAIN               |
| AdGuard DNS   | `0.0.0.0` / `::`       |
| Інші          | sinkhole-IP провайдера (потребує окремої конфігурації per-provider) |

**Підтверджено живим тестом (T-20, 2026-08-25, деталі й тестові домени —
DECISIONS.md):** обидві сигнатури — реальна поведінка живих DoH-ендпоінтів на
момент перевірки, не лише маркетингові матеріали. **n=1 на кожен провайдер**
(один тестовий домен, одна точка присутності, один момент часу) — механізм
розрізнення "блок" від "реально не існує" лишається **baseline-звірка**
(нижче), не сам факт NXDOMAIN. Для Quad9 конкретно спостережено, що
синтезований блок-NXDOMAIN приходить із порожньою authority-секцією (без
SOA), на відміну від справжнього NXDOMAIN — корисна деталь, що *підтверджує*
коректність baseline-підходу, а не самодостатня заміна йому: `is_blocked()`
(T-23) не повинен звужувати перевірку до `NXDOMAIN && authority.is_empty()`
без baseline-звірки поруч — інакше єдиний Quad9-блок із SOA в authority (не
спостережений тут, але й не виключений на n=1) тихо стає ALLOW.

**Baseline-звірка** для розрізнення "заблоковано фільтром" vs "домену реально не
існує": порівняння з нефільтруючим резолвером (напр. чистий Cloudflare/Google).
Без цього NXDOMAIN від Quad9 неможливо відрізнити від справжнього NXDOMAIN.

#### 3.2. Формат відповіді на блок

**A / AAAA → `0.0.0.0` та `::` відповідно** ("NULL blocking", дефолт Pi-hole і AdGuard).

Чому не NXDOMAIN: клієнти на NXDOMAIN часто ретраяться на інший резолвер (браузер
із власним DoH-fallback може так обійти фільтр); гірша діагностика для користувача
("сайт не існує" замість "заблоковано"); історично NXDOMAIN хайджекали ISP під
рекламу, тому частина софту має обхідну логіку. З `0.0.0.0` клієнт отримує валідну
відповідь, миттєво фейлить з'єднання локально і **не відправляє жодного пакета в мережу**.

**Чого не робити:** sinkhole на реальний IP (`127.0.0.1` чи власний вебсервер-заглушка) —
ламає локальні сервіси на тій же машині і створює плутанину.

**Інші типи записів (MX, TXT, HTTPS/SVCB) → NODATA** (успішна відповідь, RCODE=0,
порожня секція відповідей). `0.0.0.0` для них семантично безглуздий.

*Статус: рішення з загального знання про поведінку Pi-hole/AdGuard і DNS-семантику,
не з retrieved-джерела. Звірити з документацією AdGuard Home (`blocking_mode`), якщо
стане критичним.*

#### 3.3. Поведінка при таймауті апстріму

При OR-логіці, щоб відповісти "дозволено", формально треба дочекатись усіх N.
Режими (конфігуровані, дефолт — перший):

1. **`fail-open` (ДЕФОЛТ)** — апстрім, що не відповів у таймаут, вважається таким,
   що не блокує. Пріоритет доступності: один впалий провайдер не ламає інтернет.
2. **`fail-closed`** — таймаут трактується як блок. Пріоритет безпеки; ризик —
   деградація одного провайдера відчувається як "інтернет не працює".
3. **`degraded`** — відповісти по тих, хто встиг, залогувати деградацію і
   **явно показати в UI**, що фільтрація неповна (не мовчазний fail).

Таймаут — конфігурований, розумний дефолт близько 2с. Логувати кожен таймаут
(без доменних імен у логах за замовчуванням, див. Приватність).

**Уточнення реалізації (T-27, дописано заднім числом — заповнення прогалини, не зміна
вже ухваленого рішення):** текст вище буквально визначає лише "апстрім, що не відповів у
таймаут". Дві прогалини, які він не покриває явно:

- **Звичайна (не-timeout) помилка апстріму** (мережа, TLS, некоректна відповідь) —
  підпорядковується тим самим трьом режимам, що й таймаут: "не вдалось отримати
  відповідь" трактується однаково незалежно від причини. Виняток — помилка кодування
  вихідного запиту (локальна, детермінована, не мережева): вона й досі йде через ту саму
  трирежимну логіку, але логується голосніше (`error!`, не `warn!`) — під мовчазним
  `fail-open` вона б інакше перетворила кожен запит на `Allow` лише з рядком логу, а це
  саме той клас відмови, який Три Б (безпека користувача) визначає як гірший за
  відсутність фільтрації, і про який користувач не дізнається.
- **Baseline-резолвер (3.4)** як допоміжний сигнал для розрізнення Quad9 NXDOMAIN (3.1) —
  теж звичайний учасник цієї політики: якщо baseline не відповів, Quad9-блок стає
  нерозв'язним, і трактується за тим самим режимом, що й будь-який інший
  voter-таймаут (`fail-closed` → block, `fail-open`/`degraded` → allow). З Батча 3.4
  «baseline» — це вже не єдина хардкоджена адреса, а `BASELINE_CHAIN` з failover
  (T-154, §3.7); «baseline не відповів» означає, що не відповів **активний** URL
  ланцюга.

`degraded` обчислює **той самий вердикт**, що й `fail-open`, **над voters, які
відповіли** — але, на відміну від `fail-open`, свідомо **не** успадковує його
stale-if-error fallback (4.1, T-28). Різниця `degraded` від `fail-open` — виключно в
обов'язковому логуванні/прапорці неповноти голосів, не в самому обчисленні вердикту чи в
доступності stale-фолбеку.

апстрімів, не покладатись мовчки на ALPN-негоціацію за замовчуванням.

#### 3.5. GeoIP-блокування за IP-адресою відповіді

Третій, незалежний рівень фільтрації — працює не з доменом, а з фактичною IP-адресою,
яку повернув резолвер. Дозволяє блокувати за принципом "не резолвити в адреси
з країни X", незалежно від того, що каже quorum по malware/ads-категоріях.

**Джерело даних — DB-IP Lite, не MaxMind GeoLite2 (свідомий вибір, не дефолт
"бо найвідоміший").** MaxMind з 2019 вимагає акаунт і ключ ліцензії на кожне
завантаження, а з 2023 — ще й підтвердження телефону раз на 90 днів. Для
масово розповсюджуваного застосунку це або тертя на встановлення для кожного
користувача (сам реєструє акаунт), або один спільний ключ на всіх користувачів
застосунку (впирається в ліміти MaxMind, і юридично сумнівно — ключ по суті
особистий). **DB-IP Lite** — прямий download без реєстрації, ліцензія CC BY-SA 4.0,
country-рівень точності практично не відрізняється від платних баз (це і потрібно —
блок за країною не вимагає точності до міста). MaxMind лишається опційним
advanced-режимом для тих, хто хоче сам надати ключ і отримати частіші оновлення
(GeoLite2 оновлюється двічі на тиждень проти щомісячних у DB-IP Lite) — не в
дефолтній конфігурації.

**Атрибуція обов'язкова.** CC BY-SA 4.0 вимагає вказати джерело даних — рядок
в UI (About/Credits), не просто в коді.

**Позиція в конвеєрі рішень** (оновлює порядок із розділу 5):

```
1. Allowlist   → ALLOW, ні quorum, ні GeoIP не опитуються
2. Blocklist   → BLOCK
3. Cache       → взяти кешовану quorum-відповідь (домен + IP), але:
4. GeoIP-фільтр застосовується ЖИВЦЕМ навіть на кешовані відповіді
   (див. нижче, чому не кешується сам вердикт)
5. Quorum      → якщо не в кеші: опитати апстріми, отримати ALLOW + відповідні IP
6. GeoIP-фільтр на отриманих IP → якщо збіг із заблокованою країною: BLOCK
```

**Чому GeoIP-вердикт не кешується разом з quorum-рішенням, а рахується щоразу
наживо:** сама перевірка — дешевий локальний lookup у mmap-файлі (мікросекунди,
без мережі), тому кешувати нема сенсу з міркувань швидкості. А от кешувати його
разом із quorum-вердиктом означало б, що зміна списку заблокованих країн
користувачем не діє, доки не спливе TTL або не буде явна інвалідація кешу (як
у списках виключень, розділ 5). Простіше тримати GeoIP stateless-фільтром
поверх кешованої відповіді — зміна списку країн діє одразу, на наступному
запиті, без жодної логіки інвалідації.

**Політика для кількох IP в одній відповіді (CDN/anycast) — OR, з явним
попередженням про ціну.** Якщо домен повертає кілька A-записів і адреса потрапляє у заблоковану країну — блокувати всю відповідь. Це узгоджено з OR-філософією
всього проєкту, але тут ціна вища: великі CDN (Cloudflare, Google, Amazon) роздають
anycast-адреси, географія яких змінюється між запитами й точками присутності —
**високий ризик over-blocking** популярних сайтів, які просто фізично проходять
через дата-центр у "небажаній" країні, не маючи жодного стосунку до її юрисдикції.
Це не гіпотетичний edge case, а очікувана типова поведінка для будь-якого сайту
за CDN. Тому:
- Дефолтний список заблокованих країн — **порожній**. Це opt-in-рішення
  користувача, не дефолтна політика застосунку, на відміну від Security-presets
  (розділ 3.4), увімкнених з коробки.
- В UI — явне попередження при додаванні країни в блок-список: ризик заблокувати
  легітимні сайти через CDN-інфраструктуру, не саму країну походження контенту.
- В логу (розділ 6) — окреме значення `decision_source = GEOIP`, і поле з
  ISO-кодом країни, що спрацювала — щоб зі списку в один клік було видно, чи
  це справжній geo-block, чи випадковий CDN-хіт (і можна одразу додати домен
  у allowlist).

**Оновлення бази.** DB-IP Lite оновлюється щомісяця — окрема фонова задача
завантажує новий файл, **перевіряє цілісність (TLS + checksum) перед атомарною
заміною** активного файлу. Це нова категорія ризику, якої не було в решті
спека: застосунок довіряє бінарному блобу, що впливає на рішення блокування —
пошкоджена або підмінена база коштує дорожче, ніж пошкоджений кеш DNS-відповідей,
тому перевірка цілісності тут не опційна.

**Уточнення до цього пункту, T-75 (2026-08-29).** Дві речі, знайдені під час
реалізації фонового завантажувача, живим web-пошуком, не з training-пам'яті:
(1) актуальна ліцензія DB-IP Lite — **CC BY 4.0**, не CC BY-SA 4.0 як написано вище.
За живим web-пошуком 2026-08-29 (кілька незалежних джерел, жодне не саму сторінку db-ip.com),
**потім звірено напряму проти `https://db-ip.com/db/download/ip-to-country-lite` 2026-08-30 при
реалізації T-81** — сторінка сама називає "Creative Commons Attribution 4.0 International
License" і вимагає посилання назад на db-ip.com з будь-якої веб-сторінки, що показує результати
бази (сильніша вимога, ніж просто рядок атрибуції); форму цього посилання сторінка показує як

(не окремий екран "Про застосунок" — UI однобічний, без вкладок), поряд із атрибуцією MaxMind

опортуністично `.sha1`-сайдкар і за його відсутності лягає на TLS + gzip
CRC32/ISIZE-трейлер + структурну `MaxMind`-DB-валідацію як реальну гарантію
цілісності — задокументовано в `geoip_updater.rs`'s власному doc comment,

який шлях спрацював, і допишіть сюди".

**Уточнення до цього пункту, T-80 (2026-08-30) — advanced-режим MaxMind
GeoLite2.** Реалізовано як **опційний**, поза дефолтом: якщо оператор зберіг
`account_id` + `license_key` (з T-163 — в OS secret store, до того — у файлі
`geoip_maxmind.toml`), `geoip_updater.rs` переходить із DB-IP Lite на MaxMind
GeoLite2-Country. Знахідки цієї сесії
(перевірено `curl`-пробою проти живого `download.maxmind.com`, не з памʼяті):
(1) **ендпоінт** — модерний permalink
`https://download.maxmind.com/geoip/databases/GeoLite2-Country/download?suffix=tar.gz`
(відповідає `401 WWW-Authenticate: Basic realm="geoip-download"` — реальний шлях;
неіснуючий сусідній шлях дає `404`), автентифікація — HTTP Basic (account id :
license key), **ніколи не query-параметр** (щоб ключ не потрапляв ні в URL, ні в
`reqwest::Error`'s `Display` — той самий клас витоку, що вже кусав проєкт на DoH).
(2) **checksum** — шлях `?suffix=tar.gz.sha256` теж існує (`401`, не `404`), але чи
віддає він реальний дайджест на реліз — без справжніх креденшелів не підтверджено,
тож той самий опортуністичний підхід, що й для DB-IP (`.sha256`-сайдкар: наявний
mismatch — жорстка помилка; відсутній — відкат на TLS + gzip-CRC + структурну
валідацію), розширений із SHA-1 на SHA-256. (3) **формат** — GeoLite2 віддається
`.tar.gz` (архів із `GeoLite2-Country.mmdb` + `LICENSE.txt`/`COPYRIGHT.txt`), тож
доданий `tar`-крейт для розпаковки одного `.mmdb`-члена в памʼяті, обмеженого за
розміром (не хендмейд-парсер 512-байтових заголовків — той самий принцип, що й

**Уточнення, T-162 (2026-08-31) — UX MaxMind-режиму.** Реалізовано:

`keyring` і був вибором користувача (план T-67).

#### 3.6. Latency-оптимізація: early return при першому BLOCK, HTTP/2 keep-alive до апстрімів

**Early return.** OR-логіці для BLOCK-вердикту не треба чекати відповіді всіх N
апстрімів — досить одного `BLOCK`, щоб рішення було остаточним (на відміну від
ALLOW, де за 3.3 формально треба дочекатись усіх чи таймауту). Реалізація:
паралельні запити через `FuturesUnordered`; щойно перший `Future` повертає
`BLOCK` — рішення повертається негайно, а решта `Pending`-запитів позначаються
окремим статусом `CANCELED` (не `TIMEOUT` і не `ERROR` — їх свідомо не чекали,
а не "не встигли відповісти") і їхні з'єднання дропаються. Це прямий наслідок
OR-семантики, не довільна оптимізація: перший голос "за блок" вже визначає
результат.

**Наслідок для логу (6):** `voters` — крім наявних `BLOCK` / `ALLOW` / `TIMEOUT` /
`ERROR` — має п'яте значення, `CANCELED`, саме для цього випадку. Відрізняти
`CANCELED` від `TIMEOUT` важливо для діагностики: `TIMEOUT` означає "апстрім не
встиг відповісти в межах таймауту", `CANCELED` — "апстрім не був дочекатий, бо
рішення вже ухвалене іншим голосом".

**HTTP/2 keep-alive до апстрімів.** DoH-запит через `reqwest` має відчутний
оверхед на встановлення нового TLS-з'єднання за кожен запит. Тримати keep-alive
HTTP/2-з'єднання відкритими per-upstream (а не переоткривати щоразу) і задати
агресивний idle-timeout на них — інакше кожен DNS-лукап платить повну ціну
TLS-handshake до N провайдерів.

**HTTP/3 — досліджено (T-141), відкладено, не рішення проти фічі назавжди.**
Провайдерська сторона вже готова частково: Quad9 увімкнув DoH3/DoQ у березні
2026 на тому самому ендпоінті `https://dns.quad9.net/dns-query`
([dnsbenchmark.app](https://dnsbenchmark.app/blog/dns-over-quic-http3-quad9-2026/))
— співіснує з HTTP/2, не замінює його (клієнт без HTTP/3-підтримки й далі
працює звично), апгрейд узгоджується через `Alt-Svc`/DDR/SVCB, тож існуюча
жорстка HTTP/2-вимога Quad9 (CLAUDE.md gotchas) цим рішенням не порушується.
AdGuard теж модернізував протокольний набір (DoH/DoT/DoQ/DNSCrypt) у той самий
період. Cloudflare (наш baseline-резолвер, 3.1) — публічно підтверджених
DoH3-даних не знайдено, лишається DoH/DoT. Блокер — не апстріми, а власний
клієнтський стек: `reqwest` 0.13.4's `http3`-фіча explicitly unstable —
`compile_error!` без `RUSTFLAGS='--cfg reqwest_unstable'`
(`reqwest-0.13.4/src/lib.rs:252`), і сама фіча тягне `h3` 0.0.8 / `h3-quinn`
0.0.10 — обидва до-1.0. `RUSTFLAGS` тут не локальна дрібниця: це
процес-широкий прапорець, довелось би виставляти в кожній job
`.github/workflows/ci.yml`, а не лише в цьому крейті. Рішення: **не
імплементувати зараз**, повернутись, коли `reqwest` зніме
`reqwest_unstable`-гейт; тоді ж — перевірити провайдерську сторону вдруге
(Cloudflare й актуальний стан AdGuard DoH3 конкретно, не лише DoQ). Форма
майбутньої фічі (не спроєктована зараз, свідомо — SPEC.md сам застерігає
проти спекулятивних абстракцій для нереалізовної фічі): per-upstream спроба
HTTP/3 із фолбеком на HTTP/2, рішення на рівні окремого резолвера, не
глобальний перемикач.

#### 3.7. Мережевий стан, офлайн-детект і baseline-failover (Ф3 Батч 3.4 — T-152, T-154, T-155)

SPEC не мав розділу про це до Батча 3.4; три суміжні задачі про поведінку,
коли мережа/апстріми зовсім не відповідають — на відміну від 3.3, яка про
*один* таймаут. Дизайн заповнено за правилом «SPEC мовчить» (позначити
прогалину + зроблений вибір); ключові рішення — DECISIONS.md 2026-09-02,
2026-09-03.

**Multi-marker детект досяжності (T-152).** Легка періодична перевірка кількох
**незалежних** always-on маркерів (`generate_204`-класу: Google
`www.google.com/generate_204`, Cloudflare `cloudflare.com/cdn-cgi/trace`,
Apple `captive.apple.com/hotspot-detect.html`). «Сирий» вердикт циклу —
`Offline` **лише коли всі** маркери впали (один CDN-блип не фліпає), `Online`
— щойно **будь-який** відповів. **Вхід у `Offline` має гістерезис:** сервіс
публікує `Offline` тільки після `OFFLINE_CONFIRM_CYCLES` = 3 поспіль
повністю-невдалих циклів — публікація `Offline` провалює **кожен** запит
швидко (висока ставка), тож один перевантажений момент, Wi-Fi-роум чи
переконект VPN (усі три маркери перевищили таймаут за один цикл) не мусять її
тригерити; реальний обрив триває довше кількох recheck-інтервалів. **Вихід —
без гістерезису:** один успішний цикл одразу повертає `Online` (швидке
розблокування). Кеданс: idle 30 s коли стабільно `Online`, recheck 3 s поки
триває серія невдач (ще до публікації `Offline`), поки `Offline`, або одразу
після зміни вердикту. Окремий `reqwest::Client`, не спільний із DoH-клієнтом.
Пороги/маркери/кеданс — не конфігуровані (дефолти Ф3).

- *Приватність (Наскрізні вимоги).* Маркери — third-party beacon на таймері з
  privacy-focused продукту. Кожен запит — голий `HEAD` без query-параметрів і
  без даних історії; розкриває лише «ця IP-коробка онлайн», що кожен із цих
  ендпоінтів і створений приймати. Три незалежні інфраструктури, з ротацією —
  маркер-трафік не дає жодній безперервного heartbeat, і збій одного не
  підробляє «офлайн». **Окремо:** baseline-health-проба (нижче, T-154)
  **таки** шле один фіксований `example.com A` запит на *активний*
  baseline-резолвер щоцикл `Online` — безперервний heartbeat саме цьому
  оператору (зазвичай Cloudflare, і так уже baseline-резолвер 3.1 для
  реального трафіку). Без даних історії, кеданс обмежений idle-інтервалом;
  питання ВП №2 про ToS публічного резолвера для автоматичного клієнта
  стосується саме її, не маркерів.
- *НЕ підключено до `/health` чи watchdog-каналів.* `/health` навмисно
  upstream-free (§7.1 #4) — обрив мережі не повинен виглядати як мертвий
  сервіс і тригерити рестарт (саме той false positive, від якого
  мультиканальність §7 захищає).

**Офлайн → миттєвий SERVFAIL, ігнор режиму таймауту.** Коли вердикт `Offline`,
A/AAAA quorum-крок одразу віддає `SERVFAIL` — без fan-out, без читання/запису
кешу. Обґрунтування з ніші: продукт — локальний DoH-фільтр, коли мережі нема,
нема що фільтрувати й нема що резолвити; чесний стан — «резолвінг не вдався».
`0.0.0.0` на кожен домен (літеральний `fail_closed` офлайн) активно шкідливий
— браузер закешує `0.0.0.0` для справжніх доменів, і після повернення зв'язку
веб «зламаний» доки кеші не спливуть (Три Б). Режими 3.3 —
політика для «один апстрім мовчить, інші можуть відповісти», не «вся мережа
лягла». Override-списки (allowlist/blocklist) — локальні, працюють офлайн і
перевіряються раніше цього кроку. Індикатор стану (8) показує офлайн окремою
умовою #3 (між watchdog і «0 voters» — DECISIONS.md 2026-09-03).

**baseline-failover (T-154).** `BASELINE_DOH_URL` був єдиною хардкодженою
Cloudflare-адресою. Тепер `BASELINE_CHAIN` = [Cloudflare Unfiltered → Quad9
Unsecured `dns10.quad9.net` → Google `dns.google`] (§3.4 «Baseline» рядки).

- *`connect_timeout`.* Емпірична проба (kickoff): `reqwest` 0.13 переходить до
  2-ї resolved-адреси хостнейма при **швидкій** відмові 1-ї (ECONNREFUSED), але
  **НЕ** при blackhole 1-ї — доки не виставлено `connect_timeout < ` per-query
  таймаут. `ReqwestDohClient` тепер ставить 500 ms. Це відновлює IP-рівневий
  multi-A failover (Quad9 9.9.9.9 → 149.112.112.112 тощо) для обох форм відмови.
- *Sticky failover з авто-поверненням.* `BaselineSelector` (чистий стан):
  перемикання на резервний URL лише після 3 поспіль повних відмов активного;
  після перемикання — проба основного кожні 300 s, і повернення на нього щойно
  він одужав (гістерезис проти флапу). Перемикання/повернення — між запитами,
  на probe-гранулярності (не per-query retry: він б'ється з 3.6 latency й
  затримує *вердикт*, бо `combine` чекає baseline для NXDOMAIN-сигнатури).
  Писар — reachability-проб-таск; hot-path лише читає активний URL. Активний
  ендпоінт видно в `/admin/status.baseline_endpoint` (діагностика).

**Явний перемикач fallback на baseline (T-155).** Коли **кожен** enabled
filtering-voter не відповів (timeout/error, не адмін-вимкнення), вердикт
спирається на baseline / режим таймауту, не на фільтр. Цей випадок:

- завжди логується як `BASELINE_FALLBACK` (окремий рядок, що несе per-voter
  timeout-записи), а не ховається у звичайному `QUORUM`;
- перемикач `serve_baseline_when_filters_unreachable` (`resolver_config.toml` +
  `/admin/config` + `/admin/ui`), **дефолт `false`**: OFF = сьогоднішня
  поведінка, лише з чесною міткою (режим вирішує: `fail_open`/`degraded` →
  Allow через baseline, `fail_closed` → Block); ON = віддавати baseline-
  відповідь незалежно від режиму (навіть під `fail_closed`), видаючи один
  прямий baseline-запит, якщо `fail_closed` early-return лишив відповідь
  нерозв'язаною. baseline теж мертвий → чесний `SERVFAIL` у будь-якому стані
  перемикача.
- Незалежний від `timeout_mode` (той — про тлумачення *одного* мовчазного
  voter'а). Дефолт OFF розходиться з first-draft-нахилом задачі, але zero-
  регрес на дефолті — рішення користувача, DECISIONS.md 2026-09-03.
- `degraded_counts` (T-56) тепер рахує й `BASELINE_FALLBACK`-рядки (той самий
  voter-timeout-контент; це найдеградованіший стан).

### 4. Cache

**Структура даних: `moka`** (async-сумісний конкурентний кеш), не самописний
`HashMap` + мʼютекс і не простіший `lru`-крейт. Причина: потрібні одночасно три
властивості, яких стандартна колекція не дає разом — конкурентний доступ
(паралельні `tokio`-задачі читають/пишуть одночасно), **per-entry TTL** (кожен
DNS-запис має власний TTL, не єдиний на весь кеш), і розмірний ліміт (LRU-подібна
евікшн-політика). `moka` підтримує `Expiry`-трейт — обчислення часу життя для
конкретного запису в момент вставки, а не глобальну настройку. Той самий принцип,
що й вибір `hickory-dns` замість власного DNS-парсера: конкурентний TTL-кеш —
клас задач з нетривіальними race conditions, переписувати самостійно нема сенсу.

**Ключ і значення:**

```rust
struct CacheKey {
    domain: String,    // нормалізований — той самий normalize(), що й у override-списках
                        // (нижній регістр, IDN → punycode, обрізана крапка), щоб не було
                        // розсинхрону "в override один формат, у кеші інший"
    qtype: RecordType,  // A / AAAA / HTTPS / інші — різні типи мають різні TTL і відповіді
}

struct CacheEntry {
    verdict: Verdict,     // Allow(Vec<IpAddr>) | Block
    expires_at: Instant,  // абсолютний момент, не duration — не треба перераховувати
                          // залишок часу при кожному читанні, просто порівняти з Instant::now()
}
```

- Окремо кешувати сам факт "заблоковано" — блок-рішення оновлюються рідше, ніж
  живуть окремі A-записи.
- **Дефолт: не персистити на диск.** Кеш холодний після рестарту. Причина:
  кеш DNS — це фактично історія браузингу користувача; персистити її без шифрування
  неприйнятно.
- **Персистенція на диск — opt-in** (T-97, 2026-09-03): окремий (не пов'язаний із
  `persist_query_log`) прапорець `persist_cache` у `resolver_config.toml` (дефолт
  `false`). Файл `%LOCALAPPDATA%\dns-quorum-filter\cache.enc` — той самий
  `encrypted_file` / `XChaCha20Poly1305` механізм і **той самий** запис
  `persistence-key:<hash>` у OS secret store, що й `query-log.enc` (kind-байт у
  AAD-заголовку не дає відкрити один файл як інший). Флаш — повний перезапис кожні
  60 с + фінальний на graceful shutdown (не append-only). Два нетривіальні рішення:
  (1) `CacheEntry.expires_at` — монотонний `Instant`, який скидається при
  перезавантаженні, тож на диск пишеться **абсолютний настінний дедлайн**; запис,
  чий дедлайн сплив за час простою, відкидається при відновленні (RFC 8767
  stale-if-error не підключено — прострочене нема кому подавати). (2) Зберігаються
  **лише `Verdict::Allow`** — `Block` відкидається при знятті snapshot: `fail_closed`
  міг би зафіксувати таймаут-`Block` на `block_verdict_ttl` (дефолт 24 год), і
  персистенція дала б йому пережити рестарт (у т.ч. автоматичний рестарт watchdog);
  свіжий quorum-`Block` — один round-trip, OR-logic одразу переблокує. Зниклий ключ
  + наявний файл / пошкоджений файл → `.orphaned-<ts>`, новий ключ, кеш порожній.
- **Вмикання — лише правкою конфіг-файлу, без UI-тумблера** (T-97, як `persist_query_log`).
  `/admin/ui` показує окремий пасивний рядок-попередження, поки прапорець активний
  (`AdminStatusResponse.encrypted_persistence.cache`). Крос-лінк: §2 (secret
  storage), §6 (лог), Відкриті питання п.5.
- **Команда/кнопка "очистити кеш"** — обов'язкова, доступна в один клік (той самий
  принцип, що й "очистити лог", розділ 6). Потрібна практично: зміна override-списку
  вже інвалідує відповідні записи (розділ 5) точково, але користувачу має бути
  доступний і повний скид кешу вручну — наприклад, після зміни набору voters чи
  режиму таймауту, коли чекати природного TTL-протухання незручно для діагностики.
- **`Verdict::Allow` не зберігає `response_code`** — на кеш-хіті з порожнім
  списком IP (genuine NXDOMAIN/NODATA, не блок) відповідь клієнту завжди
  NODATA-вигляду (`NoError`, порожні answers), ніколи буквальний NXDOMAIN.
  Свідомий, задокументований компроміс точності при повторному читанні з
  кешу (T-39): свіжий, некешований шлях лишається точним і форвардить
  genuine NXDOMAIN як є — узгоджується з духом 3.2 (менше приводів для
  DoH-fallback браузера, не більше).

#### 4.1. Нюанси RFC, які легко пропустити при наївній імплементації

- **TTL=0 → не кешувати взагалі, не "кешувати й одразу видалити".** Різниця не
  косметична: запис із TTL=0, вставлений у `moka` навіть на мить, бере участь
  у можливих race condition при конкурентному читанні. Явна гілка: TTL=0 →
  вердикт віддається клієнту напряму, у кеш не потрапляє.
- **RFC 2181 §5.2 — TTL всередині одного RRset мають збігатися; якщо один
  апстрім повернув кілька A-записів із різними TTL в одній відповіді (можлива
  мисконфігурація чи маніпуляція) — брати мінімальний.** Це інший рівень
  розбіжності, ніж уже врахований "мінімальний TTL між N провайдерами" (3.3):
  тут — розбіжність усередині відповіді одного-єдиного апстріму. `hickory-dns`,
  ймовірно, це валідує при парсингу — перевірити явно, не покладатись мовчки.
- **Clamping TTL — мінімум і максимум, не сирі значення від апстріму.**
  Специфікація не забороняє TTL=1с чи TTL=2 роки, обидва проблемні: дуже
  низький TTL (навмисно чи через rebinding-подібну атаку) — постійні промахи
  кешу, і, важливіше для цього проєкту, часті повторні запити до N провайдерів
  означають більше витоку історії браузингу до третіх сторін (та сама
  приватнісна ціна, що обговорена в розділі "Відкриті питання"). Дуже високий
  TTL — зміна вердикту (домен став шкідливим чи перестав бути) довго не
  підхоплюється. Clamp у розумний конфігурований діапазон (дефолт: мін. 30с,
  макс. 24 год) незалежно від сирого значення апстріму.
- **RFC 2308 — негативне кешування (NXDOMAIN/NODATA) має власний TTL, з поля
  MINIMUM у SOA-записі authority-секції відповіді, не довільну цифру.** Важливо
  не сплутати два незалежні джерела TTL: TTL самого негативного кешування
  (з SOA) проти рішення "скільки кешувати факт блокування" (3.1 — уже визначено
  як "оновлюється рідше за звичайний A-запис"). Це дві різні цифри, легко
  переплутати в коді.
- **RFC 8767 (Serving Stale Data) — покращення поверх `fail-open` (3.3), не
  заміна трьох існуючих режимів таймауту.** Замість сліпого allow при таймауті
  всіх N апстрімів — якщо в кеші є протухлий, але існуючий запис, віддати його
  замість вгадування ("востаннє знав, що це було дозволено/заблоковано, довіряю
  тимчасово, поки апстріми не оживуть"). Розглянути як `stale-if-error`-стратегію
  для `fail-open`, окрему в конфігу від чистого fail-open/fail-closed/degraded.
- **CNAME-ланцюжки — TTL мінімальний по всьому ланцюжку, не тільки фінального
  запису.** Якщо домен резолвиться через CNAME A→B→C→IP, кожен хоп має власний
  TTL; кешований вердикт для початкового домену не повинен жити довше за
  мінімальний TTL з усього ланцюжка, інакше кеш переживе зміну проміжного
  CNAME-таргету. Прямий зв'язок із CNAME cloaking-детекцією (згадана на початку
  проєкту як перевага DNS-рівня над extension-блокерами): якщо `is_blocked()`
  перевіряє й проміжні CNAME-цілі, а не тільки фінальний IP, кожен хоп потребує
  власного voters-запису в логі (розділ 6) — інакше причина блоку лишається
  незрозумілою користувачу, коли трекер маскується під першу сторону.

**Доповнення (реалізація T-32/T-34/T-36, заповнення прогалини, яку текст вище не
покриває явно):**

- **`moka`'s `Expiry`-вікно = TTL запису + окреме stale-grace-вікно, не голий TTL.**
  Якщо `Expiry` видаляє запис рівно по TTL, дані, заради яких існує RFC 8767
  stale-if-error (вище), зникають з кешу раніше, ніж `should_serve_stale` встигає
  сказати "віддай їх". RFC 8767 §5 сам визначає максимальний stale-таймер
  ("suggested value is between 1 and 3 days") — це саме те вікно, `moka`'s власне
  видалення відбувається по `ttl + stale_grace`, дефолт цього проєкту — нижня межа
  діапазону (24 год, консервативний вибір). Справжня межа "свіжий/протухлий" —
  `CacheEntry::expires_at`, яка рахується при читанні, а не момент фактичного
  видалення `moka`.
- **Три незалежні "TTL у секундах" одночасно в грі цим розділом, легко переплутати
  (той самий клас плутанини, що вже названий вище для негативного кешування):**
  апстрім-похідний, clamped TTL відповіді (RFC 2181/2308-джерело, T-33/T-34/T-35/
  T-36); block-verdict TTL — константа проєкту, SPEC мовчить про число, ніколи не
  проходить той самий clamp, що апстрім-похідний TTL; і stale-grace-вікно вище —
  третє, окреме конфіг-значення. Жодне з трьох не повинно потрапити в слот іншого.

### 5. Списки виключень користувача (override lists)

Два незалежні списки, редаговані користувачем:
- **Allowlist (розблокування)** — домен завжди дозволений, незалежно від вердикту кворуму.
- **Blocklist (примусове блокування)** — домен завжди блокується, навіть якщо жоден
  провайдер його не блокує.

**Порядок застосування (фіксований, важливо для передбачуваності):**

```
1. Allowlist   → якщо збіг (тільки user-запис, 5.1 сюди НЕ належить): ALLOW,
                 ні quorum, ні GeoIP не опитуються взагалі
2. Blocklist   → якщо збіг: BLOCK, quorum і GeoIP не опитуються
3. Cache       → якщо є валідний запис: взяти quorum-вердикт з нього
4. Voter scope → якщо домену немає в кеші: визначити склад voters для Quorum —
                 домен у топ-N поточної країни (5.1) → тільки Security-tier;
                 інакше → всі увімкнені категорії
5. Quorum      → опитати визначений у кроці 4 набір апстрімів, отримати ALLOW + IP
6. GeoIP       → застосовується ЖИВЦЕМ і на кешовану, і на щойно отриману
                 ALLOW-відповідь — перевірка IP проти списку заблокованих
                 країн (див. 3.5). Не кешується разом з quorum-вердиктом.
```

Allowlist має пріоритет над blocklist — при конфлікті (домен в обох списках)
виграє дозвіл, і UI має показати попередження про конфлікт, а не мовчки застосувати.

Обґрунтування, чому overrides перевіряються **до** кворуму: економія мережевих
запитів і, важливіше, приватність — домени зі списків взагалі не витікають до
N сторонніх провайдерів.

Вимоги:
- Підтримка wildcard-збігу по піддоменах (`*.example.com`), не тільки точний збіг.
  Реалізація — суфіксний збіг по мітках домену, **не** regex і не підрядок
  (`evil-example.com` не повинен збігтися з правилом на `example.com`).
  **Wildcard-правило збігається і з самим apex-доменом** (`*.example.com`
  збігається і з `example.com`, не лише з піддоменами) — SPEC тут не мав явного
  RFC (RFC 1034 §4.3.3's wildcard-RR семантика — про інше, DNS-записи, не
  override-списки), тому обрано ту саму практику, що Pi-hole/AdGuard Home для
  цього ж класу задач (T-37).
- Нормалізація перед порівнянням: нижній регістр, IDN → punycode, обрізання
  кінцевої крапки. Інакше `Example.COM` і `example.com` будуть різними записами.
  **IDN-конвертація — строго за IDNA2008 (RFC 5891), не застарілим IDNA2003** —
  та сама версія, яку використовує `hickory-dns` для парсингу вхідних запитів;
  розсинхрон версій IDNA між нормалізацією override-списків/кешу і парсингом
  вхідного запиту означав би, що однаковий на вигляд домен інколи не збігається
  сам із собою.
- Зберігання: простий текстовий/TOML-файл в app data, редагований і вручну
  (T-145 — до цього JSON, DECISIONS.md; TOML обрано за підтримку коментарів,
  ближче до стилю `ssh_config`/`my.cnf`).
  **Відсутній файл при завантаженні — порожні списки, не помилка** (перший
  запуск, списків ще нема). **Один невалідний рядок (домен, що не парситься) у
  валідному TOML — пропускається й повертається окремо, не провалює
  завантаження всього списку** — одна друкарська помилка в одному
  blocklist-домені вручну відредагованого файлу не має мовчки розблоковувати
  решту blocklist'у (T-37).
- Зміни застосовуються без перезапуску сервісу; при зміні списків —
  **інвалідація відповідних записів кешу**, інакше старе рішення житиме до TTL.

#### 5.1. Топ-сайти по країні — виключення з Ads/Adult-voters, НЕ bypass quorum

**Виправлення власного попереднього рішення.** Спочатку цей розділ описував
топ-сайти як третє джерело allowlist-записів із повним bypass quorum. Це
суперечило явно сформульованій умові: якщо зловмисний домен випадково
проскочить у топ-N, мають "ловити" звичайні quorum-провайдери — а bypass
означає, що quorum для такого домену взагалі не запускається, ловити вже
нічим. Виправлено нижче.

**Механізм: топ-сайти виключаються лише з Ads/Adult-категорій voters (3.4).
Security-категорія лишається живою й опитується для них так само, як для
будь-якого іншого домену, щоразу, без винятків.**

- Для домену з топ-N-списку поточної країни: у quorum-запиті беруть участь
  тільки Security-tier провайдери (Quad9, Cloudflare Malware, CleanBrowsing
  Security, DNS4EU Protective), навіть якщо користувач глобально увімкнув
  Ads і Adult-категорії. Для решти доменів — усі увімкнені категорії, як і
  раніше.
- Обґрунтування узгоджується з наведеним поясненням: імовірність, що
  malware/phishing-домен потрапить у топ-50 легітимного національного
  трафіку, справді низька — тому звуження саме тут виправдане. Але це
  ніяк не стосується Ads/Adult-фільтрів (значна частина false positive
  там — не про шкідливість, а про надмірно широкі рекламні/adult-списки на
  цілком легітимних популярних сайтах) — саме цю категорію шуму фіча й
  усуває, нічого не забираючи в Security.
- **Це більше не allowlist-запис і не bypass quorum** — тому топ-сайти
  більше не проходять через override-конвеєр (5) як окремий крок "1".
  Вони впливають на **склад voters у кроці Quorum**, не на те, чи Quorum
  взагалі запускається. Оновлений конвеєр — нижче.
- Курація (fetch Cloudflare Radar → публікація версійованого списку) —
  лишається централізованою, як і було: той самий принцип уникнення
  вбудованого Cloudflare-токена в клієнтський застосунок (той самий клас
  рішення, що й з MaxMind, 3.5). Але **крос-перевірка проти quorum на етапі
  курації тепер не критична для безпеки** (Security все одно живий на
  кожному запиті) — лишається як легка гігієна списку (не включати в
  ads/adult-виняток домен, що вже явно фігурує в Security-блоклисті на
  момент курації, суто щоб не публікувати марний запис), не як захисний
  механізм.
- **Дані:** Cloudflare Radar Domain Rankings — безкоштовний, покриває 200+
  країн/територій, топ-100 денний рейтинг. N конфігурований (не обов'язково
  50) — топ-N із цього топ-100.
- **Лише точний домен, без wildcard.** Трекери/реклама часто живуть на
  піддоменах того ж registrable-домену (`ads.example.com`) — wildcard-збіг
  випадково вивів би їх з-під Ads-фільтрації разом з головним доменом, що
  прямо суперечить меті фічі.
- **Конфігурованість — саме так, як описано:** N (розмір топ-списку) і
  список країн, для яких фіча активна — обидва в UI, обидва можна вимкнути
  повністю (глобально) чи по окремій країні.
- **Неповне покриття для дрібних країн — очікувана поведінка, не помилка.**
  Radar сам зазначає, що покриття залежить від наявності регіональних даних;
  коротший список чи його відсутність для країни з малим DNS-трафіком —
  нормально, не форсувати штучний N там, де реальних ранжованих доменів менше.
- **Північна Корея — виключена практично, не політично.** Внутрішня мережа
  (Kwangmyong) не частина публічного DNS, який резолвить застосунок —
  "топ-сайтів країни" в цьому сенсі там немає, це причина відсутності даних,
  не позиція проєкту.
- **Позначення в логу.** Замість `allowlist_source` (застаріла ідея з
  bypass-моделі) — нове поле `voter_scope` (розділ 6): `FULL` /
  `SECURITY_ONLY`. Показує користувачу, чому в конкретному запиті голосувала
  не вся увімкнена конфігурація категорій.
- **Дефолт: увімкнено**, з можливістю вимкнути глобально чи по країні. Ризик
  тут суттєво нижчий, ніж у першій версії дизайну (Security ніколи не
  послаблюється), тому дефолт "увімкнено" обґрунтований упевненіше, ніж
  у попередній редакції — але формально це все ще судження, не факт,
  винесене в Відкриті питання.

**Масштаб — менший, ніж у попередній редакції, але все ще не тривіальний.**
Курація (fetch → публікація версійованого списку) лишається власним
конвеєром поза застосунком, якого немає в жодному іншому компоненті —
різниця з попередньою версією в тому, що ставки цієї курації нижчі (помилка
тут максимум повертає ads-шум на топ-сайт, не послаблює захист від malware).

##### 5.1.1. Персональний варіант — локально вивчені часто/щодня відвідувані домени

**Доповнення до 5.1, не заміна.** Той самий механізм (виключення лише з
Ads/Adult-voters, Security завжди живий, **не** bypass quorum, той самий
`voter_scope`-прапорець у логі) — але джерело списку не централізована
курація (Cloudflare Radar), а локально накопичена статистика відвідувань
цього конкретного користувача.

**Джерело сигналу — вже відфільтрований потік, не сирий трафік.** Конвеєр
(CLAUDE.md, "Request pipeline") працює абсолютно без змін — навчання не
альтернатива жодному його кроку і не окремий конвеєр, а пасивний
спостерігач поверх уже ухваленого **фінального** рішення. У лічильники
(частота, регулярність, нижче) потрапляє **лише домен, чия кінцева
відповідь користувачу — вже `ALLOW`, і саме ця відповідь пройшла (зараз чи
раніше — кеш-хіт теж рахується, інакше щоденний візит на вже закешований
домен ніколи не дав би сигналу "регулярність", а це якраз найчастіший
практичний випадок) через крок Quorum, тобто дійсно опитала (чи опитала
колись, для кешованого запису) увімкнених voters.** Домен, заблокований на
**будь-якому** кроці конвеєру — quorum'ом (Security чи Ads/Adult voter'ом,
байдуже), ccTLD, rating filter'ом, GeoIP — ніколи не потрапляє в навчання,
бо для нього сторінка не завантажується, "відвідування" не відбувається.
**Окремо виключений і протилежний край: домен, дозволений через Allowlist
(крок 1) — той термінально ALLOW ще до voter scope/quorum, voters його
взагалі не бачили.** Exemption із 5.1.1 йому нічого не дає (allowlist уже
безумовний ALLOW назавжди, voter_scope для такого запису не застосовний) —
і, що важливіше для цілісності самого механізму, включення таких доменів
зробило б хибним твердження нижче "потрапляння в навчання = вже пройдено
Ads/Adult voters сьогодні". Це не окремий режим "вимкнути фільтр і
подивитись, що піде" — фільтр лишається живим і повним під час навчання
так само, як без нього.

**Наслідок для ризику: точка відліку слабша за 5.1 (глобальний рейтинг
країни), але не відсутня, як у першому чернетковому варіанті цього розділу.**
Домен потрапляє в кандидати на exemption, лише вже пройшовши повну
конфігурацію voters, чинну на момент того вердикту — для свіжого запиту це
"зараз", для кеш-хіту не пізніше, ніж `clamp_max` (24 год, 4.1) тому, або
трохи довше під stale-if-error (T-28). Сам факт "заблокований Ads/Adult
зараз" виключає
його з навчання апріорі, тому механізм не може навчитись "вимикати" активний
блок. Те, що exemption реально робить — стабілізує вже дозволені, часто
відвідувані домени проти **майбутнього** дрейфу публічних Ads/Adult-списків
(оновлення бази хибно позначить сайт, яким користувач і так користується
щодня, роками) — та ж категорія користі, що приватність/latency (менше
запитів до N провайдерів для вже відомо-легітимних доменів, розділ
"Наскрізні вимоги"), а не послаблення поточного захисту. Residual-ризик —
не новий клас, а той самий вже прийнятий у проєкті ризик "поточний набір
voters недосконалий, не гарантія" (OR-логіка кворуму сама по собі), лише
застосований і до майбутніх voter-оновлень для цього списку.
- **Зворотний зв'язок, на який вказувала попередня редакція цього розділу,
  цим і закривається.** Курований зовнішній список незалежний від поведінки
  фільтра; навчений — залежав би, якби джерелом були всі спроби резолюції
  (відвідування → exemption → більше реклами довантажується → більше
  запитів → вищий ранг). Але оскільки лише вже-`ALLOW`-домени можуть узагалі
  потрапити в навчання, exemption сам по собі не змінює, чи реклама
  довантажується — домен і так уже не блокувався до exemption. Лишається
  дрібніший сигнал-гігієна пункт, не безпековий: рахувати
  користувачем-ініційовані резолюції (навігація), не кожен DNS-запит, який
  сторінка сама fan-out'ить під час завантаження — інакше частотний критерій
  (а) нижче штучно завищує сайти з великою кількістю subresource-доменів.
- **Два критерії включення, обидва потрібні окремо (об'єднання, не лише
  один):** (а) частота — домен у персональному топ-N за кількістю
  відвідувань у ковзному вікні (той самий принцип, що топ-N по країні в
  5.1, N конфігурований, за замовчуванням не обов'язково 50 — orientir з
  того ж порядку); (б) регулярність — домен, відвіданий щонайменше в X із
  останніх Y днів ("використовує кожен день"). Причина розділення: сайт із
  однією бурхливою сесією (багато запитів за годину) і сайт, який
  користувач відкриває коротко, але буквально щодня, обидва мають
  потрапляти в список — чиста частота відвідувань недооцінює другий випадок.
- **Зберігання — та сама дисципліна, що вже запланована для логу й кешу у
  Фазі 3 (T-96/T-97), не новий мовчазний виняток із приватнісної позиції
  проєкту — але це третє, окреме сховище, не розширення log/cache-сховищ
  T-96/T-97 самих по собі.** Щоб виявити "відвідує щодня" за X із Y днів,
  потрібна персистенція через рестарти — на відміну від log-розділу 6, де
  in-memory ring buffer (24 год/1000 записів) свідомо не переживає
  рестарт. Тут персистенція обов'язкова для самої суті фічі, тому вона
  йде під тим самим правилом: **тільки опційно, тільки шифровано** через
  платформний secure storage. Зберігати варто мінімум, потрібний для
  критеріїв вище — агреговані лічильники (домен → кількість відвідувань,
  бітмапа/лічильник днів у вікні), не сирий журнал таймстампів відвідувань
  один в один, щоб не тримати повноцінну історію браузингу довше, ніж
  функція справді потребує.
- **Дефолт: вимкнено**, на відміну від 5.1's "увімкнено" — судження, не
  факт, винесене у Відкриті питання (п.11) так само, як 5.1's власний
  дефолт у п.7. Глобальний топ-список країни — публічні, неперсональні
  дані; цей варіант розкриває поведінку саме цього користувача, і, на
  відміну від 5.1, точка відліку слабша (лише "не заблоковано конфігурацією
  voters, чинною на момент вердикту", не "низька ймовірність шкідливості в
  масштабі країни", вище) — тому приватнісна планка вища, вимагає явного opt-in і того
  самого рівня розкриття в UI, що вже вимагається для fan-out запитів до
  N провайдерів (8, п. явного повідомлення про приватність).
- Курація тут не потрібна (на відміну від 5.1) — немає зовнішнього джерела
  для звірки, список повністю локальний і належить лише цьому користувачу.
- **Відкрита DTO-прогалина, не деталь імплементації: `voter_scope`
  (`FULL`/`SECURITY_ONLY`, 6) тепер приховує дві генетично різні ситуації
  під одним значенням, не лише два джерела одного й того самого сенсу.**
  Під 5.1 `SECURITY_ONLY` означає "цей домен міг би бути заблокований
  Ads/Adult, але не опитувався" — країна-список не гарантує, що домен
  пройшов би Ads/Adult, лише що ризик malware низький. Під 5.1.1
  `SECURITY_ONLY` за конструкцією означає протилежне: "цей домен **уже**
  пройшов Ads/Adult сьогодні, і йому просто перестали задавати те саме
  питання" — потрапити в навчання інакше неможливо (вище). Один рядок логу
  з `SECURITY_ONLY` більше не відповідає на питання "чи цей домен взагалі
  колись перевірявся Ads/Adult-voters" однаково для обох джерел — це саме
  те розрізнення, яке користувач реально захоче побачити. Вирішити при
  T-138: або новий третій варіант enum'а, або окреме поле-джерело поруч
  із `voter_scope`; `UI-SPEC.md` і `diagrams/ui-dto-model.md` обидва
  зафіксували 2-варіантну версію (DECISIONS.md 2026-08-25 — `VoterStatus`,
  інший DTO, не плутати) і потребують синхронного оновлення, якщо
  `voter_scope` сам стає 3-варіантним.

#### 5.2. Блок за ccTLD країни (за доменом, не за IP — на відміну від GeoIP)

Новий, окремий механізм, паралельний GeoIP (3.5), але з іншим критерієм:
GeoIP блокує за країною **резолвленої IP-адреси** (потребує відповіді
quorum, застосовується після неї). Цей фільтр блокує за **суфіксом самого
домену** — country-code TLD (`.ru`, `.cn`, і подібні) — суто рядкова
перевірка, без жодної мережевої взаємодії чи резолюції.

- Не потребує IP, не потребує quorum — найдешевша перевірка з усіх у
  конвеєрі, тому логічно стоїть поруч з Blocklist (5), а не після Quorum,
  як GeoIP.
- Список заблокованих ccTLD — конфігурований користувачем, порожній за
  замовчуванням (той самий принцип, що й у GeoIP-країн, 3.5: не політика
  застосунку, свідомий вибір користувача).
- **Груба евристика, не надійна ідентифікація походження.** ccTLD домену
  не означає, що сайт фізично чи юридично пов'язаний із цією країною
  (домени `.io`, `.tv`, `.co` масово використовуються глобально без жодного
  стосунку до Британських Індійського океану територій, Тувалу чи Колумбії
  відповідно) — це той самий клас неточності, що й anycast/CDN-проблема в
  GeoIP (3.5), тільки в інший бік: тут хибний сигнал в самій назві домену,
  не в IP-інфраструктурі. Вартий такого самого попередження в UI, що й
  GeoIP-список країн.
- У логу (6) — окреме значення `decision_source = CCTLD_BLOCK`.

#### 5.3. Рейтинговий фільтр — найнижча вага, остання локальна перевірка перед quorum

**Перейменовано з "Curated Mode"; вибач за плутанину з "whitelist" у
попередній редакції — це не білий список, а зони доступності за
рейтингом трафіку країни.** Механізм лишається по суті тим самим
(топ-N ∪ державні ∪ науково-освітні), але виправлено дві речі: терміни
нижче і, важливіше, **позиція в конвеєрі**.

**Позиція — виправлення власної помилки.** У попередній редакції цей
фільтр стояв кроком "0", першим, перед усім іншим. Це неправильно: він
має бути **останнім локальним чекпоінтом**, після Allowlist, Blocklist,
ccTLD-блоку (5.2) і Cache — тобто останньою нагодою вирішити щось локально,
не звертаючись до мережі, перш ніж запит взагалі піде до quorum. Усі
вищі за пріоритетом механізми (user-override, ccTLD, кеш) завжди
переважають цей фільтр.

**Поведінка — лише BLOCK, ніколи force-ALLOW.** Це ключове уточнення
"найнижчої ваги": фільтр не робить домен автоматично дозволеним через
входження в топ-N/державні/науково-освітні зони — він **тільки блокує**
домени, що в жодну із зон не входять, і тільки коли явно увімкнений
користувачем. Якщо домен у зоні — фільтр просто не втручається, конвеєр
триває звично (Voter scope 5.1 → Quorum → GeoIP), як для будь-якого
іншого домену. Тобто "потрапляння в топ-N" саме тут нічого не дає само
по собі — воно вже дає ефект в іншому місці (5.1, виключення з Ads/Adult-voters),
а тут відіграє роль лише як критерій "чи взагалі пропустити цей запит
далі конвеєром".

Решта дизайну (три джерела зон, курація, дефолт "вимкнено", UI-попередження,
редакційна чутливість науково-освітнього списку) — без змін від попередньої
редакції, розписано нижче.

**Окрема фіча від 5.1, не її розвиток.** 5.1 не чіпає — voter-scope
exemption лишається дефолтною, завжди активною поведінкою для звичайного
режиму. Цей фільтр — додатковий, явно opt-in: якщо увімкнено, він блокує
домени поза зведеними зонами доступності (топ-N ∪ державні ∪
науково-освітні), **але тільки як останній локальний крок**, і тільки
блокує — не форсує дозвіл (пояснення вище). Домени всередині зон не
обходять quorum — вони просто не зупиняються на цьому кроці й ідуть
далі звичайним конвеєром (Voter scope 5.1 → Quorum → GeoIP), з усіма
увімкненими користувачем категоріями.

**Це не безпекова фіча.** Quorum і так ловить malware для всього інтернету,
з чи без цього фільтра. Це — свідоме звуження доступного простору, ближче
до батьківського контролю чи digital minimalism, ніж до захисту від загроз.
Вартий чіткого позначення в UI саме так, щоб не створювати хибне враження
"увімкнув — стало безпечніше" — стало *менше*, не безпечніше.

**Три складові зведених зон доступності, три різні моделі курації:**

1. **Топ-N сайтів країни** — те саме джерело, що й 5.1 (Cloudflare Radar),
   той самий інфраструктурний канал розповсюдження. N конфігурований, дефолт
   той самий, що й у 5.1.
2. **Державні домени, дефолт N=10 на країну.** Тут Cloudflare Radar не
   допомагає напряму — рейтинг Radar не має категорії "уряд", це рейтинг за
   трафіком, не за типом власника домену. Реалістичний підхід — **гібридний**:
   евристичне кандидування за патерном TLD/суфікса (`*.gov`, `*.gov.ua`,
   `*.gob.*` і подібні конвенції, які суттєво різняться між країнами й не
   мають єдиного стандарту) з **обов'язковим ручним рев'ю перед публікацією**
   — це не можна повністю автоматизувати надійно, бо хибне зарахування
   домену до "державного" має реальні наслідки для довіри користувача до
   списку. Це вимагає постійного редакційного процесу, не одноразового скрипта.
3. **Глобальний список науково-освітніх/некомерційних ресурсів** (PubMed,
   NASA й подібні) — **не алгоритмічний, і не per-country**. Немає рейтингового
   API для "поважні наукові сайти світу" — це виключно ручна курація,
   редакційне судження, яке потребує власного процесу рев'ю, версіонування й
   changelog. Вартий чесного визнання ризику: будь-який ручний список "що є
   авторитетним джерелом" — судження, яке можна оскаржити (чому є NASA, але
   нема аналогічної установи іншої країни; чому PubMed, а не інша
   медична база) — тримати список публічним і версійованим, щоб рішення
   курації були простежувані, а не непрозорим "чорним ящиком" усередині
   застосунку. Це той самий клас чутливості, що вже позначений для DNS4EU
   (3.4) і GeoIP по країнах (Відкриті питання) — судження про "що варте
   довіри" завжди має політичний/культурний вимір, навіть коли технічно
   нейтральне на вигляд.

**Позиція в конвеєрі — виправлена, останній локальний крок перед Quorum,
не перший (оновлює конвеєр розділу 5):**

```
1. Allowlist        → якщо збіг (user-запис): ALLOW, нічого нижче не опитується
2. Blocklist        → якщо збіг: BLOCK
3. ccTLD-блок (5.2) → якщо суфікс домену в списку заблокованих: BLOCK
4. Cache            → якщо є валідний запис: взяти quorum-вердикт з нього
5. Рейтинговий фільтр (лише якщо увімкнений користувачем, 5.3) →
   якщо домен НЕ в жодній із зон (топ-N ∪ державні ∪ науково-освітні):
   BLOCK, quorum не опитується.
   Якщо в зоні або фільтр вимкнений — не втручається, іти далі.
6. Voter scope (5.1) → визначити склад voters для Quorum
7. Quorum           → опитати визначений набір апстрімів
8. GeoIP (3.5)      → живцем на кешовану чи щойно отриману ALLOW-відповідь
```

User-allowlist (крок 1) — явний запобіжник від надто грубого "блокує геть
усе, що я хотів відкрити" — навіть з увімкненим рейтинговим фільтром
користувач може вручну додати конкретний домен поза зонами.

**Дефолт — вимкнено, без винятків.** На відміну від судження щодо 5.1
(Відкриті питання, п.7), тут це не судження — вимкнений за замовчуванням
стан обов'язковий: увімкнений з коробки режим, що блокує майже весь
інтернет, є неприйнятним сюрпризом для будь-кого, хто не вмикав його свідомо.

**Обов'язкові UI-вимоги, суворіші за звичайні тумблери категорій (3.4):**
- Не звичайний checkbox поруч з іншими — **окремий, візуально виділений
  перемикач з явним попередженням при увімкненні** ("буде недоступна
  переважна більшість інтернету, лишаться тільки топ-сайти й обрані ресурси").
  Наслідки тут на порядки серйозніші за увімкнення Adult-категорії — там
  сюрприз "заблокувало один сайт", тут — "не відкривається майже нічого".
- Індикатор стану (8) — обов'язково показує, що рейтинговий фільтр активний,
  завжди видимий, не тільки в налаштуваннях.

### 6. Лог запитів

**Конфлікт із вимогою приватності — вирішений явно.** У наскрізних вимогах стоїть
"не логувати доменні імена за замовчуванням" (лог DNS = історія браузингу). Але без
логу користувач не може діагностувати, чому сайт не відкрився. Компроміс:

- **Дефолт: in-memory ring buffer** (напр. останні 1000 записів або 24 години —
  що настане раніше). Не торкається диска, зникає при рестарті.
- **Персистенція на диск — opt-in** (T-146, реалізовано): прапорець
  `persist_query_log` у `resolver_config.toml` (дефолт `false`). Файл
  `%LOCALAPPDATA%\dns-quorum-filter\query-log.enc` — `XChaCha20Poly1305` AEAD;
  32-байтний ключ у OS secret store (`key_store`, той самий механізм, що TLS-ключ
  T-67), **ніколи не на диску**. Заголовок (`DQF1`/kind/version) — AAD, тож
  версійний cutover і підміна типу файлу — гучні названі помилки, не auth-fail.
  На відновленні застосовується той самий bounded-window (1000 / 24 год). Флаш —
  повний перезапис кожні 60 с + фінальний на graceful shutdown (не append-only;
  hard crash губить ≤60 с хвоста). Ключа нема, а файл є (Credential Manager
  очищено / теку скопійовано) → файл перейменовується в `.orphaned-<ts>`,
  мінтиться новий ключ, лог стартує порожній (query-лог — re-creatable-класу).
- **Вмикання — лише правкою конфіг-файлу, без UI-тумблера** (T-146). `/admin/ui`
  показує пасивний рядок-попередження, поки прапорець активний
  (`AdminStatusResponse.query_log_persisted`) — зберігати історію переглядів на
  диску має бути свідомий крок, а завжди-видимий банер для стану, який користувач
  сам обрав, — не анти-патерн «always-on banner ≠ попередження» (нема per-event,
  який підтверджувати). Крос-лінк: §2 (secret storage), Відкриті питання п.5.
- Кнопка "очистити лог" — обов'язкова, доступна в один клік.

Структура запису:

| Поле             | Опис |
|------------------|------|
| `timestamp`      | Час запиту |
| `domain`         | Запитаний домен (нормалізований) |
| `qtype`          | Тип запису (A / AAAA / HTTPS / …) |
| `decision`       | `ALLOWED` / `BLOCKED` / `FAILED` (SERVFAIL — resolution failed, no filtering decision was actually made; added T-147, DECISIONS.md) |
| `decision_source`| `ALLOWLIST` / `BLOCKLIST` / `CCTLD_BLOCK` / `CACHE` / `RATING_FILTER` / `QUORUM` / `GEOIP` |
| `voter_scope`    | `FULL` / `SECURITY_ONLY` — чи домен потрапив у топ-N поточної країни (5.1) і тому опитувались лише Security-tier voters |
| `voters`         | Список апстрімів із вердиктом кожного: `BLOCK` / `ALLOW` / `TIMEOUT` / `ERROR` / `CANCELED` (не дочекано через early return після першого `BLOCK`, 3.6) |
| `geoip_country`  | ISO-код країни, що спрацювала (заповнюється лише коли `decision_source = GEOIP`) |
| `resolved_ip_country` | ISO-код країни **першої** резолвленої A/AAAA-адреси у відповіді (T-161) — суто інформаційне поле, заповнюється для будь-якого рядка з реальною резолвленою IP, незалежно від `decision_source` чи того, чи взагалі налаштовано `GeoIP`-блокування; порожнє для синтетичної відповіді (blocklist/quorum-block) чи відсутньої відповіді (SERVFAIL/NXDOMAIN/NODATA). Може відрізнятись від `geoip_country` вище, коли заблокувала не перша, а інша IP у списку |
| `latency_ms`     | Загальна затримка відповіді |

`voters` — ключове поле для юзабіліті: користувач бачить не просто "заблоковано",
а *хто саме* проголосував за блок. Це дає підставу для рішення (напр. "заблокував
тільки adult-фільтр, хоча це нормальний сайт → додам у allowlist") і для діагностики
хибних спрацювань конкретного провайдера.

**Пошук по логу** — простий підрядковий фільтр по `domain` плюс фасети:
тільки заблоковані / тільки дозволені / за конкретним voter'ом. Повнотекстовий
пошук чи індексація не потрібні: обсяг у межах ring buffer тримається в пам'яті,
лінійного скану достатньо. Не ускладнювати передчасно.

З кожного рядка логу — дія в один клік: "додати в allowlist" / "додати в blocklist".
Це основний UX-цикл продукту: побачив хибний блок → виправив.

#### 6.1. Реалізація ring buffer — orthogonal до async-стану

Ring buffer — `VecDeque<LogEntry>` за `parking_lot::RwLock` (не `tokio::sync::RwLock`),
бо запис/читання логу — миттєва in-memory операція без `.await` всередині
критичної секції; `tokio`-локи виправдані там, де лок тримається через await
(мережеві/IO-операції), тут це зайвий оверхед. Дві незалежні межі буфера
застосовуються різними механізмами: розмірна межа (1000 записів) — evict
найстаршого запису при вставці, коли буфер повний; часова межа (24 год) —
фільтрація на читанні (`retain`), не окремий фоновий таск на очистку. Обидві
межі з вимоги "1000 записів або 24 години, що настане раніше" (6) — незалежні
одна від одної, спрацьовує та, що дає менший буфер у конкретний момент.

### 7. Watchdog — взаємний контроль живучості

Два процеси стежать один за одним:
- **`dnsqb-service`** — основний DoH-сервер + quorum-резолвер.
- **`dnsqb-watcher`** — легкий наглядовий процес.

Механізм: **три незалежні канали**, кожен зі своїм failure mode, замість одного —
щоб збій самого каналу зв'язку не був хибно прийнятий за смерть процесу (це і є
головний ризик, розписаний нижче).

| # | Канал | Транспорт | Що перевіряє |
|---|-------|-----------|--------------|
| 1 | IPC heartbeat | Unix domain socket (macOS/Linux) / named pipe (Windows) | Ping/pong, найшвидший. Слабке місце: файл сокета може лишитись "осиротілим" після нештатного завершення процесу. |
| 2 | Shared heartbeat-файл | Періодичний запис `mtime` у файл в app data; інший процес читає час останнього запису | Не залежить від сокет-дескрипторів; найпростіший, переживає збій IPC-стеку. |
| 3 | HTTP `/health` | Ендпоінт на вже відкритому DoH-порту (`127.0.0.1:<port>/health`) — **не новий слухач**, розширення наявного | Перевіряє не просто "процес існує", а що DoH-сервіс реально відповідає на запити — глибша перевірка, ніж канали 1-2. |

**Рішення про смерть — за більшістю каналів, не за одним.** Для напрямку
"watcher перевіряє service" (є всі три канали) — 2 з 3. Для напрямку "service
перевіряє watcher" (тільки канали 1 і 2, бо `/health` існує лише в service) —
обидва мають мовчати одночасно (unanimous), інакше поріг спрацьовує занадто
легко на двох з двох. Якщо, наприклад, тільки канал 1 мовчить, а 2 і 3 (де
застосовно) підтверджують життя — це збій IPC, не смерть процесу, рестарт не
запускається.

Інтервал перевірки — узгоджений між усіма трьома каналами (~5с), поріг — 3
пропущені поспіль **по кожному каналу окремо**, тоді підсумкове рішення — за
голосуванням.

Свідомий компроміс: три канали — це більше коду й більше поверхні для тестування,
ніж один. Це виправдано тільки тому, що ціна помилки (restart loop) — гірша за
ціну складності. Кожен канал потребує окремого юніт-тесту на "канал недоступний,
але процес живий" — інакше саме ця гілка лишиться неперевіреною й проявиться
тільки в проді.

- Watcher не отримує підтвердження життя за правилом голосування → перезапускає `dnsqb-service`.
- Service не отримує підтвердження життя за правилом голосування → перезапускає `dnsqb-watcher`.

**Головний failure mode — restart loop (обов'язково обробити).** Мультиканальність
і голосування вище — перша лінія захисту (одиничний збій каналу вже не читається
як смерть процесу). Але для напрямку "service перевіряє watcher" каналів усього
два (IPC + shared-файл, без `/health`), тому там голосування слабше — потрібен
**unanimous** (обидва канали мовчать), не просто більшість, інакше поріг спрацьовує
занадто легко на двох з двох. Додатково, як друга лінія захисту (на випадок, якщо
й обидва канали одночасно деградували, а процес насправді живий):
- Перед перезапуском — перевірити, чи процес реально мертвий (за PID, не тільки за
  відсутністю heartbeat). Відсутність heartbeat ≠ мертвий процес.
- Експоненційний backoff між спробами перезапуску.
- Ліміт спроб у вікні часу (напр. 5 за 10 хв) → далі зупинитись, показати помилку
  в UI, **не** продовжувати цикл. Тихий нескінченний restart loop гірший за явну
  зупинку з повідомленням.
- Single-instance guard (файловий лок / named mutex) на кожен процес — щоб перезапуск
  не породив другий екземпляр поруч із живим першим.

**Додатково: `dnsqb-watcher` — точка входу автозапуску, не лише heartbeat-монітор
(обговорено 2026-08-27, будується разом із рештою Фази 3, T-150).** Інсталятор реєструє
Startup-ярлик/Run-ключ (Windows) на `dnsqb-watcher`, не напряму на `dnsqb-service` — за
аналогією з ланчером типу Steam. На запуску (зокрема при вході користувача в систему)
`dnsqb-watcher` ідемпотентно перевіряє стан обох інших процесів (той самий single-instance
guard/PID-механізм, що й вище) і піднімає відсутнє: `dnsqb-service`, якщо не запущений;
`dnsqb-tray`, якщо не запущений. Повторний запуск ярлика (випадковий подвійний клік, ручний
рестарт) іде тим самим шляхом і нічого не дублює, бо перевірка стану — перед стартом, не
безумовна. Це не новий канал чи механізм — та сама watchdog-роль `dnsqb-watcher`, лише одна
додаткова відповідальність (запустити відсутнє, а не тільки рестартнути мертве). Свідомо не
будується раніше Фази 3 — до появи single-instance guard/PID-перевірки (T-89/T-92) ланчер-роль
мала б дублювати ту саму логіку окремо, тимчасово, у процесі, що інакше — заглушка.

Обидва процеси — під звичайним користувачем, без підвищених прав. Watcher свідомо
тримати мінімальним за функціоналом: чим менше в ньому коду, тим менша ймовірність,
що впаде саме він.

**Це не safety-critical**, а UX-механізм: якщо обидва процеси мертві, браузер просто
фейлить DoH і йде у власний fallback — інтернет працює, фільтрація ні. Тому watchdog
зобов'язаний **повідомити** про проблему в UI, а не тихо намагатись полагодити.

#### 7.1. Реалізаційні рішення (Фаза 3, Батч 3.0 — 2026-09-01)

Проза §7 вище лишає відкритими конкретні механізми й числа («named mutex / файловий лок»,
«напр. 5 за 10 хв», «експоненційний backoff»). Батч 3.0 (kickoff Фази 3, plan-mode + advisor)
їх фіксує — щоб кожен наступний watchdog-батч (3.1–3.3) не переоткривав те саме рішення.
Діаграми `diagrams/watchdog-state.md` і `diagrams/watchdog-channels.md` малюються з цієї
підсекції як з джерела.

1. **IPC-транспорт (канал 1).** Windows: `tokio::net::windows::named_pipe` — safe, уже в
   дереві через `tokio`, жодного raw `CreateNamedPipeW` FFI, `#![forbid(unsafe_code)]`
   лишається цілим (той самий підхід, що `keyring` для secret store, T-67). Ім'я каналу:
   `\\.\pipe\dns-quorum-filter\heartbeat-<h>`, де `<h>` — перші 8 hex від sha1 нормалізованої
   (lowercase, без хвостового роздільника) app-data теки — та сама ізоляційна деривація, що в
   `key_store` entry name, тож scratch-екземпляр у власній app-data теці не колідить з
   реальним. Unix (Фаза 6): domain socket у app-data з тим самим `<h>`-суфіксом, за
   `#[cfg(unix)]` seam.
   **Ролі: `dnsqb-service` — сервер каналу** (створює `heartbeat-<h>`, довговічніший і
   завжди присутній процес), `dnsqb-watcher` — клієнт (конектиться). **Один дуплексний
   pipe, ping/pong обох напрямів мультиплексовані на ньому** (не два pipe). Після
   дисконекту клієнта сервіс піднімає новий `NamedPipeServer`-інстанс і знову чекає
   `connect` — так відновлення після рестарту watcher'а не потребує окремого коду.
   **Слабке місце «осиротілий сокет» з таблиці §7 — Unix-only:** іменований pipe Windows —
   kernel-об'єкт без артефакту у ФС, зникає, коли закрито останній хендл; на Windows-таргеті
   цього failure mode немає, будувати захист від нього не треба.
2. **Single-instance guard (T-92).** Свій advisory lockfile, без нових залежностей і без
   `unsafe`: `std::fs::OpenOptions` + `std::os::windows::fs::OpenOptionsExt::share_mode(0)`
   (повністю ексклюзивний хендл) на `<app-data>/<role>.lock`, `role` ∈
   `service` / `watcher` / `tray`. Хендл тримається відкритим на весь час життя процесу; OS
   закриває його при завершенні, зокрема при краху → лок звільняється сам, осиротілого стану
   немає. Per-user app-data тека вже дає per-сесійну ізоляцію, тож namespace-префікс
   (`Global\` / `Local\`, як у named mutex) не застосовний і підвищені права не потрібні —
   на відміну від `Global\`-mutex, який вимагав би `SeCreateGlobalPrivilege` і суперечив би
   вимозі §7 «обидва процеси — під звичайним користувачем». Розглянуті й відхилені крейти:
   `single-instance` 0.3.3 (не оновлювався ~4 роки, тягне `winapi` 0.3 — старий FFI-стек — і
   `widestring` 0.4), `fslock` 0.2.1 (теж без підтримки), `named-lock` 0.4.1 (підтримується,
   але тягне `windows` 0.53 — велику bindings-родину, іншу ніж `windows-sys` у `keyring`).
   Unix (Фаза 6): `flock(LOCK_EX | LOCK_NB)` на тому ж файлі — та сама форма API за
   `#[cfg(unix)]` seam.
3. **PID-файли — джерело PID для перевірки перед рестартом.** Кожен процес при старті (уже
   тримаючи свій guard з п.2) пише `<app-data>/<role>.pid` з `{ pid, exe_path, started_at }`
   (serde). `dnsqb-watcher` і ланчер-роль T-150 читають ці файли — без них, коли обидва
   процеси піднято незалежно при вході користувача в систему (нормальний сценарій за T-150),
   watcher не має child-handle й **немає звідки взяти PID** для перевірки «чи процес реально
   мертвий». Перевірка живучості (Батч 3.2, через вет-крейт типу `sysinfo`, не raw FFI) звіряє
   PID **і** `exe_path` / ім'я процесу проти вмісту pid-файлу — bare-PID перевірка читала б
   recycled PID як «живий назавжди», і watchdog ніколи не перезапустив би справді мертвий
   сервіс: тихий вічний збій, гірший за restart loop, якому §7 присвячує весь свій розділ про
   failure mode. Життєвий цикл файлу: **перезаписується при кожному старті процесу, свідомо
   не видаляється при виході** — залишковий pid-файл від мертвого/recycled PID коректно
   відсіює перевірка ідентичності вище, тож окремий cleanup-крок (і його власний failure
   mode) не потрібен.
4. **Wire-формат heartbeat.**
   - *Канал 1 (pipe)* — мала фіксована структура, не JSON (watcher свідомо мінімальний — §7).
     Кадр: `[u16 LE довжина][u8 версія = 1][u8 kind][u64 LE seq][u64 LE unix_millis]`,
     `kind` ∈ `Ping = 1` / `Pong = 2`. Парсер — чиста функція
     `parse_frame(&[u8]) -> Result<Frame, FrameError>`, окремо від сокет-I/O (pure/impure
     розділення — «Наскрізні вимоги»).
   - *Канал 2 (shared-файл)* — **лише `mtime`**: періодичний write-touch, рішення про staleness
     — суто `now − mtime > поріг`, крапка (§7: «найпростіший»). Без payload-парсингу на шляху
     рішення, без atomic-rename — звичайний перезапис. Вміст файлу — фіксований маркер
     (magic + `role` + `schema_version`), записаний один раз при створенні; якщо при читанні
     маркер не збігається (чужий / зіпсутий файл зі свіжим `mtime`), канал 2 віддає «нема
     сигналу» (не «смерть») і лог один раз. Ця розбіжність визначена тут явно, а не лишена на
     імплементацію.
5. **Шлях до бінарників для spawn.** `std::env::current_exe()?.parent()` →
   `dnsqb-service.exe` / `dnsqb-tray.exe` / `dnsqb-watcher.exe` поруч. Ніколи PATH-lookup
   (PATH — atacker-influenceable input, не константа — «Наскрізні вимоги»). Якщо `current_exe`
   повертає незвичайний шлях (симлінк, тимчасова тека) — hard error, не мовчазний
   PATH-fallback.
6. **Спільний код.** `dnsqb-watcher` додає `dnsqb-service = { path = "../dnsqb-service" }` як
   lib-залежність (так само, як `dnsqb-tray` для `AdminClient`). Переспільне: `paths`
   (app-data тека), DTO `/health`, деривація `<h>` з п.1. **Рефактор у Батчі 3.1:** винести
   sha1-хелпер нормалізованої app-data теки з `key_store` у `paths` як `pub`, щоб і ім'я pipe,
   і secret-store entry брали одну деривацію, а не дві копії.
7. **Файл стану watchdog.** `dnsqb-watcher` — **єдиний письменник**
   `<app-data>/watchdog-state.json` (serde; атомарний replace через temp + rename). Поля:
   `schema_version`, `state` (enum: `Healthy` / `ChannelDegraded` / `SuspectDead` /
   `VerifyingPid` / `Restarting` / `BackoffWait` / `GaveUp` — див. `watchdog-state.md`),
   `target` (`service` / `watcher` — до кого стан), `restart_attempts_in_window`,
   `window_started_at`, `last_transition_at`, `last_error: Option<String>` (грубий текст, без
   доменів і без чутливого — «діагностичні логи не містять доменних імен»). `dnsqb-tray`
   полить цей файл (як уже полить `/admin/status`); `/admin/status` отримує поле
   `watchdog: WatchdogStatusView`, читаючи той самий файл (Батч 3.3 / T-95). `dnsqb-service` і
   `dnsqb-tray` — тільки читачі. **Відома залежність T-95:** відкритий ⚠️ GAP у
   `diagrams/ui-status-indicator.md` (порядок пріоритету умов індикатора, коли кілька
   виконані одночасно) «потребує підтвердження чи явного запису в DECISIONS.md перед
   реалізацією T-56/T-95» — Батч 3.3 має його закрити, не переоткрити.
8. **Інтервал, поріг, backoff, бюджет — числа, яких §7 не дає (дефолти Ф3, не конфігуровані
   в Ф3).** Інтервал опитування — 5 s, спільний тик для обох напрямів. Поріг — 3 пропущені
   поспіль **по кожному каналу окремо**, тоді голос. Backoff між спробами рестарту —
   1 → 2 → 4 → 8 → 16 s (cap 16 s). Бюджет — 5 рестартів у вікні 600 s, далі `GaveUp`.
   `GaveUp` — **per-target**: `service` і `watcher` мають окремі лічильники, вікна й стани.
9. **Рантайм `dnsqb-watcher`.** `tokio` current-thread (`rt`, не `rt-multi-thread` — watcher
   мінімальний), features `rt` / `net` / `time` / `process` / `sync` / `macros`.
10. **Канал 3 — довіра до self-signed cert.** `/health` живе на DoH-порту, тобто за `rustls`
    із самопідписаним листовим сертифікатом (§2, `cert.rs`). `dnsqb-watcher` опитує його **тим
    самим шляхом довіри, що `dnsqb-tray`** — через `admin::AdminClient::new(app_data_dir,
    port)`, який читає `cert.pem` з app-data теки й робить `reqwest::Certificate::from_pem` +
    `.add_root_certificate` (T-48/T-52). **Ніколи `danger_accept_invalid_certs`.** Через T-69
    (ротація сертифіката) канал 3 **не пінить trust anchor на весь час життя процесу**: клієнт
    каналу 3 перебудовується з `cert.pem` на кожному циклі (пере)конекту / після виявленого
    рестарту сервісу, а не один раз на старті. (Пере-використання `AdminClient` — ще один
    пункт «спільного коду» п.6.)

### 8. UI

> **T-149 (DECISIONS.md): Tauri-вікно замінено треєм + вбудованим веб-UI.** Прозова частина
> цього розділу нижче (рядок 4, Tauri IPC allowlist, `#[tauri::command]`, CSP webview) описує
> дизайн, актуальний **до** цього реверсу — принципи (явний allowlist поверхні, типізовані DTO,
> чотири категорії тестів каналу) лишаються дійсними й застосовними до нового HTTP-based каналу
> (рядки 12a/12b вище), але буквальний Tauri-механізм (`invoke`/`emit`, webview CSP) — історичний
> контекст, не поточна реалізація. Не переписано рядок за рядком — цей розділ описує здебільшого
> ще не побудований майбутній повний UI (T-53–T-60, більшість усе ще відкриті), а не лише два вже
> поставлені Ф1-екрани; UI-SPEC.md має власну примітку, де саме чернетка розходиться з реально
> поставленим.

**Екранний inventory, таблиці полів по кожному екрану, DTO-діаграми, чернетка
Tauri-command allowlist і графічний мокап — у [`UI-SPEC.md`](UI-SPEC.md) і
[`diagrams/`](diagrams/).** Цей розділ лишається джерелом дизайн-рішень і
обґрунтування; UI-SPEC.md їх не переказує, лише посилається сюди за номером.

**Два різні канали, не один** — рядок 4 (webview JS ↔ Tauri-процеса власне Rust-ядро,
`invoke`/`emit`) і рядок 12 (T-52, той самий Tauri-процес ↔ окремо запущений `dnsqb-service`, HTTPS
на loopback DoH-порту). Команда типу `set_providers` перетинає обидва: webview кличе Tauri-команду
(ряд 4), та команда сама йде в мережу до `dnsqb-service` (ряд 12) і повертає результат назад.
Allowlist нижче стосується ряду 4 (що видно з webview) — ряд 12 не експонує довільного доступу до
адмін-каналу, лише те, що конкретна команда сама вирішила туди передати.

**Канал UI↔бекенд (рядок 4 таблиці вище) — явний allowlist команд, не відкритий
міст.** Tauri за замовчуванням дозволяє експонувати довільні Rust-функції в JS
через `#[tauri::command]`; без свідомого обмеження це легко перетворюється на
широку, погано контрольовану поверхню — той самий принцип мінімальної поверхні,
що вже застосований до watcher'а (7) і до привілеїв інсталяції (2). Вимоги:
- Команди, доступні з webview, — явний, короткий, задокументований список
  (перегляд/пошук логу, редагування override-списків, зміна конфігурації
  апстрімів/GeoIP, статус сервісу). Внутрішні структури бекенду (наприклад,
  сирий `CacheEntry` чи деталі quorum-запиту) не експонуються напряму — тільки
  DTO, призначені для UI.
- Події від бекенду до UI (новий запис логу, зміна статусу деградації) —
  той самий принцип: мінімальний, типізований набір подій, не потік
  внутрішнього стану "як є".

**Формат DTO — internally tagged enum через serde, дзеркальний до TS discriminated
union.** `VoterStatus` (Pending/Block/Allow{ip_count}/Error{message}/Canceled, 3.6)
серіалізується з `#[serde(tag = "status", rename_all = "SCREAMING_SNAKE_CASE")]`;
на фронтенді це відповідає union-типу `{ status: 'ALLOW', ip_count: number } | ...`
— TypeScript звужує тип по полю `status` без ручного парсингу чи `any`. Той самий
підхід для решти DTO логу (`LogEntry`, `decision_source`, `voter_scope`) — жодне
поле не має бути вільним рядком там, де множина значень скінченна й відома
наперед, це і є практичне виконання вимоги "тільки типізовані DTO" вище.
- Content Security Policy webview — обмежена, без `unsafe-inline`/`unsafe-eval`
  за замовчуванням (Tauri дозволяє це налаштувати в конфігу застосунку).

**Базова статистика (некритична, пізня фаза) — лічильники, обчислені живцем із
логу (6), без нового сховища.** Кількість оброблених доменів і відсоток
заблокованих — тривіальний підрахунок по `decision`-полю вже наявних записів
`LogEntry`. Топ відвідуваних сайтів — рейтинг доменів у межах поточного
ring-buffer вікна (6) за кількістю входжень, той самий обсяг даних, що вже
доступний пошуку по логу, просто інша візуалізація. **Не плутати з 5.1.1** —
це знімок поточного in-memory логу (не переживає рестарт, як і сам лог), без
персистенції, без критеріїв частоти/регулярності, без жодного впливу на
voter scope; суто UI-зручність поверх уже наявних даних.

#### 8.1. Тести каналу UI↔бекенд — чотири окремі категорії, не одне "smoke"

"Smoke" сам по собі перевіряє тільки, що щось не падає при нормальному сценарії —
цього мало для каналу, який приймає вхід від webview (недовіреного середовища
за замовчуванням: XSS у самому UI, скомпрометований рендер, чи просто помилка
розробника — усе це в результаті шле довільний виклик у той самий IPC-міст).
Чотири окремі категорії, кожна зі своєю метою:

| Категорія | Мета | Приклади конкретних кейсів |
|-----------|------|------------------------------|
| **Smoke** | Кожна команда з allowlist викликається з валідним вхідом і повертає очікувану форму відповіді; застосунок стартує з прикріпленим UI без падінь | Виклик кожної команди по черзі при холодному старті; перевірка, що events (новий запис логу, зміна статусу) реально долітають до UI |
| **Злам (security/exploit)** | Довести, що канал не дає більше, ніж дозволено allowlist'ом, навіть при недовірі до webview | Виклик команди, якої немає в allowlist (симуляція компрометованого JS) — очікувано: відмова, не тиха деградація; спроба передати шлях за межі app data в командах, що працюють з файлами (path traversal); величезний payload (мегабайти в одному полі) — перевірка, що є ліміт розміру, не необмежена алокація; спроба ін'єкції в override-список через поле домену (символи новго рядка, лапки, керуючі байти — щоб не зламати JSON-серіалізацію файлу і не підробити сусідні записи логу) |
| **Неправильне використання (misuse)** | Легітимний користувач робить нелогічну, але можливу через UI дію — система має лишатись у передбачуваному, безпечному стані, не падати й не давати сюрпризів | Додати домен одночасно в allow і blocklist (вже описано — конфлікт, попередження); **вимкнути всіх voters одночасно через UI** (новий кейс, розписаний нижче); імпорт вручну відредагованого override-файлу з биту JSON або з мільйоном записів (файл редагується вручну за задумом, розділ 5 — має оброблятись без падіння, з чіткою помилкою парсингу користувачу); швидке багаторазове перемикання одного тумблера поспіль (гонка між UI-подією і станом бекенду) |
| **"На дурня" (fuzz / надійність)** | Випадковий чи навмисно "дурний" вхід (порожні рядки, non-UTF8 байти, екстремальні числа, неправильні типи) у кожну команду не викликає паніки (`unwrap()`/`panic!` на межі IPC — заборонено), а повертає типізовану помилку | Property-based / fuzz-тест (`proptest` чи `cargo-fuzz`) на кожну команду, що приймає рядок чи число від UI — ціль: жодна команда не панікує на довільному вхідному байтовому наборі |

**Новознайдена прогалина, яку виявило саме "misuse"-мислення: що робити, якщо
користувач вимикає всіх voters одночасно?** До цього моменту спек не визначав
цей стан явно. Порожній набір voters — не просто "менше покриття", а
структурно інша поведінка: OR-логіка (3) над порожньою множиною некоректна
семантично (немає кого опитувати, немає й голосу "за блок"). Рішення:
**трактувати як явний pass-through** — резолюція йде через baseline-резолвер
(3.4) без жодної фільтрації, а не як `fail-closed` (блокувати все, бо "нема
кому дозволити" — несподівано й неюзабельно) і не мовчки як "нічого не
змінилось". **Індикатор стану в UI (вже задокументований) повинен показувати
цей стан окремим, явним написом** ("фільтрацію вимкнено — жодного активного
провайдера"), відмінним від "деградований апстрім" — це не збій, а свідомий
вибір користувача, але користувач має точно знати, що зараз відбувається.
Цей кейс — окремий рядок у переліку `is_blocked()`/quorum-тестів (Наскрізні
вимоги), не лише в тестах UI-каналу.

- Мінімальне вікно налаштувань: тумблери апстрімів, вибір режиму таймауту,
  статистика заблокованого.
- **Індикатор стану — обов'язковий**, не опційний: чи браузер справді використовує
  локальний DoH, чи фільтрація активна, чи є деградовані апстріми, чи живий watchdog.
  Мовчазна непрацююча фільтрація — гірше за явно вимкнену.
- **Вкладка логу запитів** із пошуком, фасетами і колонкою `voters`; дія
  "в allowlist / в blocklist" в один клік із рядка.
- **Редактор списків виключень** із підсвіткою конфліктів (домен в обох списках).
- **Налаштування GeoIP** — список заблокованих країн (порожній за замовчуванням),
  з попередженням про ризик over-blocking через CDN при додаванні країни, і
  індикатор дати останнього оновлення бази.
- ~~**Явне повідомлення про приватність кворуму** (див. Ризики п.4) — не заховане
  в дрібний шрифт.~~ **Реверс 2026-08-28 (DECISIONS.md)** — вимогу скасовано за
  прямим рішенням користувача.

## Фазований план

**Крок 0 — Таблиця стандартів + тести на відповідність (перший крок реалізації,
до будь-якого коду резолвера).**

Обґрунтування порядку: наскрізний принцип цього спека — "RFC, а не інтуїція чи
поведінка конкурента" (див. Наскрізні вимоги). Щоб цей принцип не лишався
декларацією, першим артефактом реалізації має бути не код, а явна таблиця:
кожен пункт — конкретна вимога з конкретного RFC, розділ спека, де вона вже
згадана, і **тест, що перевіряє відповідність цій вимозі, написаний до того, як
існує код, який має її задовольняти.** Тобто спочатку падаючий тест на RFC-вимогу,
потім імплементація, що робить його зеленим — не навпаки.

| RFC | Назва | Вимога до проєкту | Розділ спека |
|-----|-------|--------------------|--------------|
| RFC 1035 | Domain Names — Implementation and Specification | Базовий wire format, структура запиту/відповіді — фундамент, на якому стоїть `hickory-dns` | 1, 3 |
| RFC 2181 | Clarifications to the DNS Specification | TTL всередині одного RRset мають збігатися; якщо ні — мінімальний | 4.1 |
| RFC 2308 | Negative Caching of DNS Queries (DNS NCACHE) | TTL негативного кешування (NXDOMAIN/NODATA) — з поля MINIMUM у SOA, не довільна цифра | 3.1, 4.1 |
| RFC 5891 | Internationalized Domain Names in Applications (IDNA2008): Protocol | IDN → punycode нормалізація override-списків і ключа кешу, версія узгоджена з `hickory-dns` | 5 |
| RFC 6891 | Extension Mechanisms for DNS (EDNS(0)) | Розширений формат запиту/відповіді, розмір UDP-пакета | 3.4 |

| RFC 4033–4035 | DNSSEC (Introduction, Resource Records, Protocol) | Quad9 Filtered валідує DNSSEC — якщо застосунок передає AD-біт клієнту, має зберігати коректність цього сигналу, не підробляти | 3.4 |

**Примітка щодо ECH (T-14, перевірено 2026-08-25):** Encrypted Client Hello
відтоді формалізовано як **RFC 9849** (опубліковано березень 2026 IESG) — на
момент написання початкової редакції спека це справді була IETF-чернетка, але
статус змінився. Не змінює жодного рішення цього документа (HTTPS/SVCB і так
проксіюються повз quorum саме через ECH-залежність, розділ 3) — лише знімає
застереження "чернетка, не стандарт". Не додано окремим рядком у таблицю
RFC-стандартів вище, бо ECH сам по собі не DNS-протокол, а TLS-розширення, що
транспортується через HTTPS RR (RFC 9460, уже в таблиці) — цей запис лишається
приміткою, не новим рядком.

Таблиця не претендує на вичерпність — якщо під час реалізації якогось компонента
виникне протокольне питання поза цим списком, перший крок — знайти відповідний
RFC і додати рядок у таблицю, а вже потім писати код проти нього. Тести з цієї
таблиці — окрема секція conformance-тестів у CI, незалежна від юніт-тестів на
бізнес-логіку (розділ "Наскрізні вимоги"), щоб регресія проти самого стандарту
була видна окремо від регресії проти власних рішень проєкту.

**Фаза 1 — Proof of concept (1 платформа: macOS або Windows)**
- Rust DoH-сервер + quorum з 2 апстрімів (Quad9 + AdGuard DNS).
- Self-signed leaf-сертифікат, встановлений **вручну** в trust store (без автоматизації).
- Списки виключень (allow/block) + in-memory лог запитів із колонкою `voters` —
  входять у MVP, бо без них неможливо діагностувати хибні спрацювання під час
  вимірювання метрик нижче.
- Watchdog — **не** в Фазі 1 (виносити у Фазу 3): на етапі PoC ручний перезапуск
  прийнятний, а взаємний heartbeat додає складності без користі для перевірки гіпотези.
- Ціль: перевірити ланцюжок end-to-end (браузер → локальний DoH → quorum → апстріми →
  рішення → кеш) до вкладання в кросплатформну автоматизацію.
- Метрики: затримка на холодному vs теплому кеші; detection rate кворуму vs кожен
  окремий провайдер на тестовому наборі відомих malicious-доменів (перевірити, чи
  кворум справді ловить більше за найкращий одиночний провайдер — це емпіричне
  питання без відповіді до вимірювання).

**Фаза 1 формально закрита 2026-08-29 (TASKS.md's закриттєвий план) — закриття про поставку
(deliverables, бул-список вище), не про валідацію (Ціль і Метрики нижче — обидві лишаються
відкритими, див. далі в цьому абзаці).** Кожен пункт бул-списку вище виконано на рівні резолвера: quorum (2 апстріми) реально працює, self-signed leaf
встановлюється (спершу вручну, потім автоматизовано понад MVP-вимогу — T-49), override-списки +
in-memory лог є, без watchdog'а (як і планувалось). **Один явний, не приховуваний розрив,
знайдений closing-advisor-рев'ю перед цим самим комітом**: "Ціль" вище прямо називає ланцюжок
"браузер → локальний DoH → quorum → ...", але жоден зафіксований тест ніколи не проганяв саме цю
першу ланку — реально налаштований Chrome із `https://127.0.0.1:<port>/dns-query` як Custom DoH
provider, що резолвить через нього живий домен. Усе, що є: DoH-клієнтський рівень
(`Invoke-WebRequest -HttpVersion 2.0`, T-143/T-148) і Chrome-automation проти `/admin/ui` (інша
сторінка, не сам DNS-канал) плюс підтверджена довіра сертифіката (T-49/T-51 — передумова, не сам
прохід). Названо явно, не замовчано (той самий стандарт, що вже в T-47: "якщо не можеш
протестувати UI — скажи це прямо"). Метрики (T-66) виміряні — кворум на зібраному зразку **не**
показав приросту над Quad9 самим по собі (AdGuard 0/38, n=1) — це та сама гіпотеза, яку "Ціль"
вище називає умовою "до вкладання в кросплатформну автоматизацію": результат не підтверджує
вкладання в Фазу 2 як специфіковано, і чи продовжувати за планом, чи спершу переміряти/додати
третього провайдера — відкрите рішення, не вирішене цим закриттям. Два пункти з TASKS.md's Ф1-
секції лишаються відкритими backlog-рядками (T-51's Firefox-половина, T-56's повний
браузер-usage-check і watchdog-стан) — обидва явно поза оригінальним бул-списком цієї фази (не
названі тут вище) і поза MVP-скоупом (заблоковані на T-132/T-134 відповідно), тож не блокують це
закриття. Наступною активною фазою була Фаза 2 — вона стартувала рішенням користувача *попри*
відкритий метрик-гейт і незафіксований живий Chrome-Custom-DoH-прохід (обидва перелічені вище);
Фаза 2 закрита 2026-08-31 (див. її блок нижче), гейт несеться далі у Фазу 3 як відкритий.

**Фаза 2 — Автоматизація сертифіката (Windows). Формально закрита 2026-08-31.**
- Сертифікат-примітиви — **готово**: генерація self-signed leaf з типізованими IP-SAN (T-48),

- **Пакетований інсталятор/деінсталятор** (MSIX) — **перенесено у Фазу 3** (T-156 + T-70):
  первинна вимога "інсталятор генерує/ставить, деінсталятор прибирає сертифікат **і** ключ із
  secure storage" виконана лише на рівні примітивів + tray-driven install; пакування самого
  інсталятора заблоковане на MSIX-роботі, яка й так у Фазі 3.
- **UI для додавання кастомного DoH-провайдера** (довільний URL) — **готово** (T-72/T-73):

- **GeoIP-блокування** (розділ 3.5) — **готово** (T-74–T-82): DB-IP Lite дефолт + опційний

  `/admin/ui`-картка списку заблокованих країн, атрибуція.
- T-164 (opt-in Quad9 9.9.9.11 ECS-preset) — **відхилено 2026-08-31** (розділ 3.4).

**Закриття Фази 2 не закриває Ф1-метрик-гейт** (T-66: кворум не показав приросту над найкращим
одиночним провайдером; живий Chrome-Custom-DoH-прохід не зафіксовано) — гейт несеться у Фазу 3.
`DEFAULT_PROVIDER_IDS` (`upstream.rs`) досі `quad9`+`adguard`, не §3.4/§3.5-й "лише Security" —
відкрите рішення без номера, свідомо не змінене у T-72/T-73, несеться далі.

**Фаза 3 — Продакшн-hardening**
- Watchdog: окремий процес `dnsqb-watcher` із взаємним heartbeat (розділ 7),
  backoff і лімітом спроб перезапуску.
- **Пакетований інсталятор/деінсталятор** (MSIX, T-156): деінсталятор викликає
  `trust_store::uninstall()` **і** `key_store::delete_secret` для TLS-запису ключа (T-70,
  перенесено з Фази 2 — Windows-половина; macOS-половина у Фазі 6).
- Опційне шифроване персистентне зберігання логу і кешу (DPAPI / Keychain /
  Secret Service).
- Enterprise policy автоматизація (Chrome `DnsOverHttpsMode=secure` + `DnsOverHttpsTemplates`
  через `HKLM\SOFTWARE\Policies\Google\Chrome`, `REG_SZ`) — механізм звірено з першоджерелом
  T-98 (2026-09-04, tiered-докази в §"Відкриті питання" п.3). **T-99 закрито без коду
  2026-09-04** (рішення користувача на kickoff, той самий формат, що T-164): `secure` робить
  Chrome-резолвінг hard-fail при мертвому `dnsqb-service` (Три Б user-safety), запис
  `HKLM\...\Policies` потребує адмін-прав і глобальний для машини — конфлікт із «без постійних
  підвищених прав»; фіча Chrome-only — той самий висновок, що T-134 для Firefox. Пом'якшення
  Відкритого питання п.10 лишається за індикатором стану (T-56). Механізм задокументовано для
  можливої майбутньої фази, не реалізовано.
- Детальний батч-план виконання (9 батчів, порядок, per-batch plan+advisor gate) —
  **TASKS.md §"Фаза 3", блок "План виконання Ф3"** (2026-09-01). Глибокий дизайн watchdog
  лишається тут, у §7; порядок виконання — робота TASKS.md, той самий поділ, що для Ф2.

**Фаза 4 — Виключення топ-сайтів з Ads/Adult-voters (розділ 5.1)**
- Окрема фаза, не частина Фази 2/3: єдина позиція спека, що вимагає власного
  серверного/CI-конвеєра курації (fetch Cloudflare Radar → публікація
  версійованого списку доменів по країнах), а не лише клієнтського коду.
  Інфраструктурно важча за GeoIP (3.5), де застосунок просто завантажує
  чужий готовий файл — але **не безпекова фіча**, на відміну від початкової
  редакції: Security-quorum лишається живим для цих доменів завжди, тому
  ставки помилки тут — ads-шум, не послаблений захист.
- Передумова: Фаза 2 (розповсюдження версійованих файлів з перевіркою
  цілісності) уже має бути готова й обкатана на GeoIP — тут той самий
  клієнтський механізм, новий тільки конвеєр курації.
- Метрика перед стартом: наскільки часто в реальному QA топ-N-домени
  фальшиво спрацьовують саме в Ads/Adult-категоріях (3.4), а не в Security —
  якщо цей false positive rate і без того низький, цінність фічі варто
  переоцінити, а не імплементувати за замовчуванням "бо було заплановано".

**Фаза 5 — Рейтинговий фільтр (розділ 5.3) та ccTLD-блок (5.2)**
- ccTLD-блок (5.2) — набагато легша задача за решту цієї фази: чисто
  рядкова перевірка суфікса домену, без залежності від жодної зовнішньої
  курації. Технічно міг би піти раніше (навіть у Фазу 1), але я не переношу
  його туди самовільно — MVP-скоуп Фази 1 лишаю як є вище, це лише
  зауваження про складність, не рішення про зміну плану.
- Рейтинговий фільтр (5.3) — передумова: Фаза 4 готова (переюзовує
  інфраструктуру топ-N по країнах).
- Найбільша редакційна (не інженерна) складова проєкту: список державних
  доменів і науково-освітній список вимагають постійного людського рев'ю,
  не одноразового скрипта — закладати в план не як "фіча", а як **процес**,
  що триває й після релізу.
- Явно не MVP і не рання фаза для основної частини: це нішева, потенційно
  рідковживана функція (звуження всього інтернету) — розумно вводити тільки
  після підтвердження, що є реальний попит, не проактивно "про всяк випадок".

**Фаза 6 — Друга / третя десктопна платформа (macOS, Linux)**
- **Свідомо остання фаза, винесена в кінець навмисно.** До цього моменту ціль —
  одна платформа (Windows), бо середовище розробки не має macOS build/test-доступу
  (Keychain API, `security` CLI). Це **не** "може колись" — планова ціль, просто
  остання за чергою, щоб платформно-специфічна робота не розповзалась по Фазах 2–3.
- Автоматизація trust-store install/uninstall на macOS — Keychain,
  `security add-trusted-cert` (T-68/T-70 macOS-половини; Windows-половини готові, T-49).
- Порт `dnsqb-service` + `dnsqb-tray` на macOS (T-71). Linux — можлива третя ціль
  із **ручною** інсталяцією сертифіката (той самий підхід, що для Windows у Фазі 1);
  automated NSS DB install лишається окремим epic'ом ("Явно поза межами MVP" нижче).
  Це про Linux як **другу десктопну платформу** (графічний UI лишається); headless-режим
  (сервер без графічної оболонки) — окреме, архітектурно не вирішене питання
  ("Відкриті питання" пп.12-13), не входить сюди.
- CI build matrix розширюється на macOS (і Linux, якщо додається як ціль) — T-83.
- **Вимога до всіх попередніх фаз (архітектурний інваріант):** платформна специфіка
  ховається за абстракційними межами, які виносяться під `#[cfg(target_os)]` / трейт
  **без переписування**, не хардкодяться безповоротно на Windows. Стан на 2026-08-31:
  `key_store` (через `keyring`) уже так спроєктований — Windows Credential Manager /
  macOS Keychain / Linux Secret Service за одним API; `trust_store` цю межу **ще не
  має** (ні трейта, ні `#[cfg(target_os)]`) — порт будує її з нуля, названо явно
  заздалегідь, щоб не було сюрпризом. Будь-який spawned system process (`certutil`,
  `rundll32`) сьогодні резолвиться абсолютним шляхом від `%SystemRoot%` — на
  macOS/Linux еквіваленту немає, потрібна платформна гілка.

## Явно поза межами MVP

- Cosmetic filtering / element hiding — задача uBlock-класу, DNS-рівень цього
  принципово не робить.
- Кросплатформна NSS DB автоматизація для Linux — окремий epic (**не** те саме, що
  "Linux як ціль" загалом — Фаза 6 допускає Linux із ручною інсталяцією
  сертифіката; поза MVP тут лише сам automated trust-store install).
- System-wide DNS override — свідомо відкинутий через проблему crash-recovery.
- Merge публічних блок-листів (EasyList тощо) — окрема фіча, не частина quorum-логіки.

## Наскрізні вимоги (безпека / якість)

- **Дефолтна поведінка при неоднозначності — відповідний RFC, не інтуїція чи
  поведінка конкретного продукту-конкурента.** Це загальний принцип для всього
  проєкту: якщо в реалізації виникає питання "як правильно" і в цьому спеку
  немає явної відповіді — звірятись зі специфікацією (повний перелік базових
  RFC — таблиця в "Крок 0" на початку Фазованого плану), а не копіювати
  поведінку Pi-hole/AdGuard Home наосліп чи вгадувати. Прецеденти інших
  продуктів — корисний орієнтир для UX-рішень (напр. формат блок-відповіді, 3.2),
  але не заміна специфікації для протокольної поведінки. Якщо RFC сам залишає
  простір для інтерпретації (як з `fail-open`/`fail-closed`, де специфікація не
  диктує конкретної політики) — тоді рішення ухвалюється явно й документується
  тут, а не мовчки успадковується з чужого коду.
- Мінімум привілеїв: підвищені права **тільки** одноразово для trust store, ніколи
  постійно. Основний процес — під звичайним користувачем.
- Жодних мережевих слухачів, крім loopback.
- `#![forbid(unsafe_code)]` у всіх крейтах проєкту, де це можливо; будь-який `unsafe`
  потребує явного обґрунтування в коментарі.
- Логи: доменні імена тримаються **лише в in-memory ring buffer** (див. розділ 6);
  запис на диск — тільки opt-in із шифруванням. Діагностичні логи самого сервісу
  (помилки, таймаути) доменних імен не містять.
- CI: `cargo audit` (відомі CVE в залежностях) + `cargo deny` (ліцензії, дублікати)
  як обов'язкові кроки, не рекомендація. Плюс CodeQL SAST-скан (`.github/workflows/codeql.yml`,
  мова `rust`, `build-mode: none`) на кожен push/PR — знахідки тріажаться й фіксяться в тому ж
  проході, не лишаються відкритими бо решта гейтів зелена (T-101).
- Тести: обов'язково — юніт-тести на `is_blocked()` per-provider, на quorum-логіку
  з мокнутими апстрімами, на порядок застосування overrides, на суфіксний
  wildcard-збіг (щоб `evil-example.com` не збігався з `*.example.com`), і на
  GeoIP-фільтр (OR по кількох IP в одній відповіді, коректна поведінка коли
  список країн порожній — nop, не помилка), і на **порожній набір voters
  (pass-through, не fail-closed)**; на **voter scope для топ-сайтів (5.1)**
  — Security-tier voters завжди опитуються, навіть коли домен у топ-N
  списку і Ads/Adult-провайдери з voters виключені (регресія тут означала б
  тихе послаблення саме security-захисту, а не тільки ads-шум — найбільш
  чутливий тест до цієї фічі); окремо — на watchdog voting-логіку
  (2-з-3 і unanimous-гілки, і саме сценарій "один канал мовчить, процес живий" —
  це найважливіший тест у всьому watchdog-модулі, бо регресія тут напряму
  відтворює restart loop). Це ядро продукту, регресія тут = тихий пропуск загроз,
  хибне блокування або нескінченний перезапуск процесів.
- Тест на ccTLD-блок (5.2) — чиста функція, домен із забороненим суфіксом
  блокується без будь-якого мережевого виклику (навіть без Cache/Quorum-моків).
- Тест на рейтинговий фільтр (5.3) — домен поза зонами доступності блокується
  без звернення до quorum (перевірка, що quorum-моки взагалі не викликаються
  — економія мережі й приватність, а не просто правильний вердикт); домен
  усередині зони не отримує force-ALLOW, а продовжує звичайний конвеєр
  (regression-тест саме на "лише BLOCK, ніколи force-ALLOW" — легко
  переплутати при імплементації); user-allowlist як явний виняток працює
  навіть з увімкненим фільтром.
- Тести каналу UI↔бекенд — окремо задокументовані в 8.1 (smoke, злам, misuse,
  fuzz), включно зі snapshot-тестом на allowlist експонованих Tauri-команд.
- Reproducible builds / підписані релізні бінарники — застосунок ставить довірений
  сертифікат у систему, тому довіра до самого бінарника критична.
  **Стан (Батч 3.7, T-100/T-102/T-103, 2026-09-04):**
  - *Репродукованість (T-100).* Три ноги: `rust-toolchain.toml` пінить точну версію;
    `Cargo.lock` трекається і `--locked` стоїть на кожному `cargo` виклику в CI;
    `.cargo/config.toml` дає `link-arg=/Brepro` (детермінований PE `TimeDateStamp`,
    лише для `x86_64-pc-windows-msvc`) + `[profile.release] codegen-units = 1`
    (типове `16` планує codegen між потоками недетерміновано — на великому
    `dnsqb-service` це давало різні байти з однакових джерел). CI-джоба `repro`
    робить дві чисті `--release` збірки в **різних абсолютних теках**
    (`--remap-path-prefix` тоді задіяний) і падає, якщо SHA-256 трьох бінарників
    не збігаються. Блокуюча. Доведено на закріпленому toolchain + образі раннера
    `windows-latest` (4 послідовні зелені прогони); інший Windows SDK → інший
    `link.exe` → байти можуть відрізнятися, цю вісь CI не перевіряє.
  - *Підпис (T-102).* CI підписує бінарники (не бандл) у `.github/workflows/release.yml`.
    Модель (рішення користувача, kickoff 2026-09-04): реальний сертифікат необов'язковий —
    якщо задано secret `CODESIGN_PFX` (+`CODESIGN_PASSWORD`), він використовується
    строго; інакше крок генерує **ефемерний self-signed** сертифікат у раннері
    (приватний ключ не виходить за його межі, не в git, не в secret) і бінарники
    марковано `test-signed`. Продакшн-довіра приходить від **пере-підпису Microsoft
    Store** при публікації MSIX (Батч 3.8), не від цього кроку. Ім'я артефакту несе
    режим (`test-signed` / `signed`) — прогін ніколи не «просто бінарники» без
    вказаного стану підпису.
  - *Реліз (T-103).* Тег `v*` → джоба `release`: повторно доводить cross-path
    репродукованість для цього тегу → завантажує підписаний артефакт → створює
    **чернетку** GitHub-релізу з трьома `.exe` + `SHA256SUMS`. Публікує людина
    вручну. MSIX-пакет — іменована прогалина для Батча 3.8 (T-156), не тут.
    `per-OS` = лише Windows (macOS/Linux → Фаза 6).
- Атрибуція DB-IP Lite (CC BY-SA 4.0) в UI (About/Credits) — юридична вимога
  ліцензії, не опційна.
- Перевірка цілісності (TLS + checksum) перед атомарною заміною GeoIP-бази при
  автооновленні — бінарний блоб, що впливає на рішення блокування, потребує
  того ж рівня довіри, що й сам бінарник застосунку.

## Відкриті питання / ризики (потребують рішення чи перевірки, не факти)

1. ~~**Формат блок-відповіді**~~ — **вирішено, T-20 (2026-08-25), DECISIONS.md.**
   Для Cloudflare підтверджено офіційно (`0.0.0.0`). Для Quad9 і AdGuard —
   тепер підтверджено живим тестом (не лише маркетинговими матеріалами):
   Quad9 → NXDOMAIN з порожньою authority-секцією; AdGuard → `0.0.0.0`/`::`.
   Деталі й тестові домени — DECISIONS.md.
2. **ToS апстрімів** — чи дозволяють Quad9 / AdGuard DNS автоматизовані DoH-запити
   від стороннього клієнтського застосунку. Не перевірено; юридична звірка потрібна
   до публічного релізу.
3. **Chrome DoH enterprise policy — звірено з першоджерелом (T-98, 2026-09-04).**
   Джерело: `chromium.googlesource.com/chromium/src/+/main/components/policy/
   resources/templates/policy_definitions/Miscellaneous/DnsOverHttpsMode.yaml`
   + `DnsOverHttpsTemplates.yaml` (гілка `main`, fetched 2026-09-04). Гоча для
   наступних сесій: `chromeenterprise.google/policies/*` — JS-рендер, WebFetch
   бачить лише оболонку; `chromium.googlesource.com` `.yaml` fetch-иться;
   `admx.help` цього дня лежав (522).

   **Первинне (Chromium `policy_definitions` YAML):**
   - `DnsOverHttpsMode` — Chrome 78+ (Android 85+, ChromeOS 78+). Enum
     `off` / `automatic` / `secure`. `secure` = «надсилає лише DoH-запити й
     повертає помилку резолву при збої» — **без тихого фолбеку на нативний
     резолвер** (це і є механізм, потрібний п.10 нижче). `dynamic_refresh: true`
     (застосовується й відкочується без рестарту Chrome), `per_profile: false`
     (глобально для браузера, не per-profile).
   - `DnsOverHttpsTemplates` — Chrome 80+. **Обов'язковий і непорожній, коли
     `mode = secure`.** Кілька резолверів — URI-шаблони через пробіл. `{?dns}`
     у шаблоні ⇒ GET, інакше POST. **Некоректний шаблон мовчки ігнорується**
     (у `secure` це = усі запити провалюються без діагностики). Приклад:
     `https://dns.example.net/dns-query{?dns}`.

   **Вторинне (сторонні hardening-гайди CleanBrowsing/NextDNS + Google support
   `answer/9131254`):** реєстр `HKEY_LOCAL_MACHINE\SOFTWARE\Policies\Google\
   Chrome`, обидва значення `REG_SZ` (також `HKCU\SOFTWARE\Policies\Google\
   Chrome` — per-user, без адмін-прав). Google support 9131254 явно описує
   реєстровий шлях як механізм «для комп'ютерів, не приєднаних до AD-домену».

   **Не закрито цим проходом:** чи DoH-політики входять у Chromium
   `kSensitivePolicies` (малий список, ігнорований на *не*-керованій машині) —
   джерельний масив цим проходом дістати не вдалося (2 спроби, 3-attempt rule).
   Проти цього: hardening-гайди покладаються на роботу цих політик на
   standalone-Windows, і Google 9131254 документує не-AD-шлях. Остаточна
   перевірка — емпіричний `chrome://policy` на цільовій машині — винесена в
   kickoff T-99.

   **Наслідок для T-99:** `secure` + шаблон `https://127.0.0.1:<port>/
   dns-query{?dns}` закриває п.10 для Chrome, але робить Chrome-резолвінг
   **жорстко залежним** від живого `dnsqb-service` (watchdog 3.0–3.3 пом'якшує,
   не усуває hard dependency). Запис `HKLM\...\Policies` потребує адмін-прав і
   глобальний для машини — конфлікт із «без постійних підвищених прав»
   (Наскрізні вимоги), той самий, що вже названо для Firefox (T-134). Chrome-
   only; Edge — та сама схема під `HKLM\SOFTWARE\Policies\Microsoft\Edge`.
   Передумови, дві з яких провалюються тихо: шаблон містить конфігурований порт
   (оператор змінює порт → застаріла політика, а некоректний шаблон мовчки
   ігнорується), і Chrome має вже довіряти T-49 leaf-сертифікату, інакше
   endpoint не працює.

   **Рішення (2026-09-04):** T-99 закрито без коду (kickoff-AskUserQuestion,
   формат T-164) — hard-fail-залежність + конфлікт із «без постійних підвищених
   прав» + Chrome-only переважили; той самий висновок, що T-134 для Firefox.
   Механізм лишається задокументованим тут для можливої майбутньої фази.
   **Незакритий підпункт лишається відкритим, не знятий:** перед будь-яким
   майбутнім відродженням T-99 його треба закрити емпірично (`chrome://policy`
   на не-AD-машині — чи `HKLM`/`HKCU` DoH-політики взагалі застосовуються поза
   доменом, чи фільтруються як `kSensitivePolicies`). Негативний результат
   перетворює «відхилено через posture привілеїв» на «недоступно взагалі» — це
   різні висновки, і другий міняє, чи фазу варто планувати. Див. Фазований
   план, Фаза 3.
4. **Приватність кворуму:** N провайдерів замість одного означає, що історія
   браузингу видима одразу N сторонам на кожен новий (не кешований) домен. Це
   об'єктивно **гірше для приватності**, ніж один провайдер, в обмін на краще
   покриття загроз. ~~Має бути явно комуніковано користувачу в UI, а не прихована
   деталь архітектури.~~ **Реверс 2026-08-28 (DECISIONS.md)** — явне UI-повідомлення
   (T-57) прибрано за прямим рішенням користувача; сам компроміс, описаний вище,
   залишається фактом архітектури, лише вимога явного UI-розкриття скасована.
5. **Персистентність логу/кешу** — тримати in-memory (дефолт) чи шифроване на
   диску. **Вирішено й реалізовано** для обох (окремі прапорці, спільний механізм
   `encrypted_file` / `XChaCha20Poly1305` / один `persistence-key` у OS secret
   store, вмикання лише конфіг-файлом + пасивний індикатор): *лог* — T-146,
   2026-09-03 (`persist_query_log`, §6); *кеш* — T-97, 2026-09-03
   (`persist_cache`, §4 — лише `Allow`-вердикти, абсолютний настінний дедлайн,
   прострочене за простій відкидається).
6. **GeoIP-блокування за країною — політично чутлива функція за своєю природою**,
   не суто технічна. Незалежно від того, наскільки нейтрально реалізована (порожній
   дефолт, попередження про over-blocking), сама наявність "блокувати за країною
   походження IP" — це та сама категорія рішень, що й занепокоєння щодо DNS4EU
   вище (розділ 3.4): інструмент, застосовний і для законного захисту, і для
   довільного геополітичного фільтрування. Тримати нейтральним технічно (без
   вбудованих дефолтних списків країн), але усвідомлювати, що ця фіча — не
   рівнозначна ads/malware-фільтрації за ризиком неправильного застосування.
7. **Виключення топ-сайтів з Ads/Adult-voters (5.1) — дефолт "увімкнено" усе
   ще судження, але з нижчими ставками, ніж у первинній редакції.** Після
   виправлення (Security-quorum лишається живим завжди) компроміс звузився
   до "менше ads/adult-шуму на популярних сайтах" проти "трохи ширша
   поверхня, якщо якийсь топ-домен раптом стане джерелом реклами/adult-контенту
   між оновленнями списку" — набагато дешевша помилка, ніж послаблений захист.
   Дефолт "увімкнено" обґрунтований упевненіше, але формально не факт.
   Окремо не перевірено: чи Cloudflare Radar API ToS дозволяє таке використання
   даних (публікація похідного списку доменів як частини стороннього продукту) —
   та сама категорія перевірки, що вже позначена в п.2 для Quad9/AdGuard.
8. **Рейтинговий фільтр (5.3) — дефолт має бути "вимкнено", без обговорення, на
   відміну від п.7 вище.** Це єдиний пункт у спеку, де я не залишаю питання
   відкритим: увімкнений за замовчуванням режим, що блокує переважну
   більшість інтернету, — неприйнятний UX-сюрприз, не варте обговорення
   судження. Питання, яке справді відкрите: сам державний і науково-освітній
   список — хто саме курує, за яким явним критерієм включення/виключення,
   і як часто переглядається. Список типу PubMed/NASA виглядає нейтральним
   технічно, але будь-який ручний вибір "що варте довіри" — редакційне
   судження з культурним/політичним виміром, навіть коли автори не мали
   такого наміру. Публічність і versioning списку (розділ 5.3) — часткове
   пом'якшення, не повне вирішення цього ризику.
9. **Certificate Transparency-політики браузерів щодо leaf-сертифіката на
   `127.0.0.1` (розділ 2) — не перевірено емпірично.** Chrome/Chromium мають
   жорстку CT-вимогу для публічно довірених сертифікатів; для приватного/
   loopback-хоста, доданого користувачем локально в trust store (не через
   публічний CA), зазвичай є виняток, але це варто підтвердити на реальних
   поточних версіях Chrome і Firefox під час імплементації Фази 1, а не
   покладатись на загальне уявлення про політику CT.
10. **Мовчазний браузерний DoH-fallback повністю обходить кворум — не
    закрито технічним рішенням у поточному спеку.** Якщо `dnsqb-service`
    відповідає таймаутом чи помилкою, браузер за замовчуванням може тихо
    перейти на резолвер за системними/дефолтними налаштуваннями замість
    локального DoH — весь кворум-механізм (2) для цього сеансу зникає без
    жодного сповіщення користувача, і ніщо в поточному дизайні цього не
    ловить. Технічно закрити це можна лише примусовим "secure mode" DoH
    у браузері (Chrome `DnsOverHttpsMode=secure` через enterprise policy —
    той самий канал, що вже позначено як неперевірений у п.3), а це
    вимагає адмін-рівня налаштування, не одноразового підтвердження, і
    конфліктує з принципом "без постійних підвищених прав" (Наскрізні
    вимоги). Мінімальне часткове пом'якшення без enterprise policy —
    індикатор стану (8) повинен явно детектувати й показувати, коли
    браузер фактично НЕ використовує локальний DoH (а не лише "чи сервіс
    живий"), але це діагностика постфактум, не запобігання витоку.

    **T-134 (2026-08-28, дослідження — TASKS-DONE.md), два уточнення.**
    (1) Firefox має прямий аналог enterprise-політики, названої вище лише
    для Chrome: політика `DNSOverHTTPS` (`Locked` + `network.trr.mode`/
    `network.trr.uri`), режим 3 (TRR-only) — Firefox-відповідник Chrome's
    `DnsOverHttpsMode=secure`, без тихого фолбеку на нативний резолвер.
    Той самий застережувальний висновок застосовується однаково: це
    адмін-рівня налаштування, не одноразове підтвердження користувача,
    той самий конфлікт із "без постійних підвищених прав". (2) Для
    non-enterprise/локальної половини — того, що реально потрібно T-56
    для власного індикатора стану — жоден пасивний сигнал на боці
    `dnsqb-service` (тиша в log-вікні) не може надійно відрізнити "браузер
    тихо перейшов на інший резолвер" від "користувач зараз не активний" —
    фундаментально неоднозначно з боку сервера самого по собі. Єдина
    знайдена техніка з реальним прецедентом (клас DNS-leak-test сторінок
    інших DoH-провайдерів) — активний клієнтський canary-запит із
    `/admin/ui`: домен, чия єдина коректна відповідь можлива лише через
    власний резолвер `dnsqb-service`, який сторінчин власний JS
    намагається дістати. **Потрібна нова примітивна можливість, якої зараз
    немає** — перевірено (не припущено): `overrides::OverrideLists::
    decision` повертає лише бінарний `Option<ListKind>` (Allow/Block),
    `wire::build_block_response` жорстко кодує `0.0.0.0`/`::`, і ніщо в
    поточному конвеєрі не вміє прив'язати довільний домен до довільної
    фіксованої "canary"-IP — знадобиться окремий, ще не спроєктований
    маршрут/механізм, не розширення наявного override-списку. Правдоподібність
    самого підходу (не готовність примітиву) підтверджена WebSearch —
    Chrome дійсно проводить звичайну сторінкову DNS-резолюцію, не лише
    навігацію, через сконфігурованого кастомного DoH-провайдера. **Не
    перевірено емпірично** (потрібен окремий scratch-прогін перед довірою,
    той самий стандарт, що й решта проєкту) — і поведінка Firefox's TRR на
    рівні сторінкового `fetch` окремо цим проходом не підтверджена.
    Firefox's власний reverse-canary домен (`use-application-dns.net`) —
    інша механіка (перевірка, чи *мережа* блокує DoH, через нативний
    резолвер при старті/зміні мережі), не переноситься напряму на потребу
    T-56 (детекція з боку самого сервісу). T-98 (звірка офіційної
    документації Chrome `DnsOverHttpsTemplates`) лишається окремою
    задачею Фази 3, цим проходом не поглинута.

    **T-98/T-99 (2026-09-04).** T-98 звірив механізм із першоджерелом
    (Chromium `policy_definitions` YAML — деталі в п.3): `DnsOverHttpsMode
    =secure` дійсно вимикає тихий фолбек на нативний резолвер, і `+
    DnsOverHttpsTemplates=https://127.0.0.1:<port>/dns-query{?dns}` технічно
    закрив би цей пункт для Chrome. **T-99 (автоматизація запису політики)
    закрито без коду** — той самий застережувальний висновок, що вже
    зафіксовано вище для обох браузерів: адмін-рівня, машинно-глобальне
    налаштування конфліктує з «без постійних підвищених прав», а `secure`
    робить увесь Chrome-резолвінг hard-fail при недоступному `dnsqb-service`.
    Індикатор стану (T-56) лишається єдиним пом'якшенням, як і планувалося.
11. **Персональний варіант топ-N (5.1.1) — дефолт "вимкнено" судження, не
    факт, і ризик тут слабший, ніж у першій редакції цього пункту, але не
    нульовий.** Навчання джерелом бере лише домени, чий вердикт кворуму з
    усім поточним набором voters (Security + увімкнені Ads/Adult) уже
    `ALLOW` — заблокований зараз домен апріорі не може потрапити в
    exemption-кандидати, тому механізм не "вимикає" активний захист і
    структурний зворотний зв'язок (exemption → більше реклами → більше
    відвідувань → вищий ранг) не виникає: exemption не змінює, чи домен
    зараз резолвиться, лише знімає майбутні Ads/Adult-запити до нього.
    Залишковий ризик — вужчий: чи "дозволено конфігурацією voters, чинною на
    момент вердикту" — достатня підстава довіряти домену проти **майбутніх** оновлень
    Ads/Adult-списків (а не проти поточного стану, як помилково
    стверджувала попередня редакція цього пункту). Це той самий клас
    ризику, що вже прийнятий для quorum OR-логіки загалом (набір voters
    недосконалий, не гарантія), лише розтягнутий у часі на майбутні
    оновлення списку для конкретних, часто відвідуваних доменів — не
    перевірено емпірично, наскільки це прийнятне розширення, вирішується
    при імплементації (T-138). Дефолт "вимкнено" лишається виправданим
    окремо через вищу приватнісну планку особистих даних (5.1.1), не
    потребує цього ризику як додаткової причини.
12. **Кросплатформність за межами Windows, включно з headless-режимом (Linux-сервер
    без графічної оболонки) — ціль, архітектурно ще не вирішена.** `dnsqb-service`
    сам по собі (`tokio`/`hyper`/`rustls`) не має UI-залежностей, але зараз жорстко
    Windows-only на рівні коду, не лише "ще не портовано": `paths.rs`/`cert.rs`/
    `tls.rs` читають `%LOCALAPPDATA%` напряму (`PathsError::LocalAppDataNotSet` на
    відсутність), а `cert.rs` обмежує ACL приватного ключа через `icacls.exe`
    (`%SystemRoot%\System32\icacls.exe`) — на Linux/macOS цих інструментів немає.
    Портування вимагає заміни цих конкретних місць (наприклад, крейт `directories`
    замість `%LOCALAPPDATA%`, `chmod 600`/`std::os::unix::fs::PermissionsExt` замість
    `icacls`), не просто перекомпіляції під іншу ціль. `dnsqb-ui` (Tauri) додатково
    вимагає графічної сесії (X11/Wayland чи Windows-десктоп) для рендеру нативного
    webview — на headless Linux (сервер без монітора) не запуститься **за
    конструкцією**, незалежно від того, наскільки портовано сам резолвер. Якщо
    headless-керування стає реальною ціллю (а не лише "Linux як друга десктопна
    платформа", вже згадане у Фазованому плані для Фази 2 в контексті trust-store),
    постає окреме архітектурне рішення про сам UI-шар — див. п.13.
